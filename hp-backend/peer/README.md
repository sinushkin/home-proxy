# `peer` — CLI-обвязка над `connection`

Поднимает `MultiLink` — менеджер динамического набора UDP-дыр до одного пира (от
`HOLES_MIN` = 4 до `HOLES_MAX` = 10 в работе, срок жизни дыры `HOLE_AGE`, по умолчанию `180-600` с;
эти три переменные окружения можно задать и здесь) — и логирует число живых дыр. Само устройство
(набор дыр, рандеву, пробив, keep-alive) — в `../connection`.

## Запуск

```
peer <stun_addr[,stun2_addr]> <mqtt_addr> <mqtt_ca> <my_peer_id> <peer_id>
```

`<mqtt_ca>` — путь к PEM-файлу с CA-сертификатом брокера (`ca.crt`, см.
`../../cert/README.md`): к MQTT ходим только по TLS (порт `8883`), а адрес
брокера проверяется по SAN сертификата, поэтому здесь нужен именно тот адрес
(IP), который в него вписан. `ca.crt` публичный, его копируют на каждый пир.
`<my_peer_id>` брокер видит как `client_id`, `<peer_id>` — как `username`, и по
ним ACL разрешает писать только свои дыры и читать только дыры искомого пира
(`../../mosquitto/README.md`).

Оба GUID'а — заранее известные "имена" пиров (не общий секрет, не
генерируются на лету). `my_peer_id`/`peer_id` местами меняются между двумя
инстансами — у каждого свой на первом месте. Локальные порты (по одному на
дыру) назначает ОС — руками не задаются.

## Быстрый запуск: `run.sh`

`run.sh` берёт настройки из `.env` рядом с собой, выставляет логи и запускает
`peer`, так что остаётся только запустить. Образец `.env` — `.env.example`
(`STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA`, `MY_PEER_ID`, `PEER_ID`; сам `.env` в git
не попадает). У второй стороны `MY_PEER_ID` и `PEER_ID` меняются местами.

```bash
./run.sh                      # логи наших крейтов на уровне debug (по умолчанию)
LOG_LEVEL=info ./run.sh       # только INFO: состояния и сообщения [#N]
```

`LOG_LEVEL` можно вписать и в `.env`; полная строка `RUST_LOG` там же главнее.
В чекауте скрипт сам пересобирает `peer` через `cargo`; на хосте без cargo
берёт готовый бинарник `./peer` рядом со скриптом. Для хоста без cargo нужны
рядом: `peer`, `run.sh`, `ca.crt`, `.env` (`MQTT_CA=./ca.crt`).

## Пример: живой прогон на двух хостах

STUN и MQTT — debug-стек на `profit` (см. корневой `CLAUDE.md`). GUID'ы ниже
просто пример — для своего прогона сгенерируйте два новых (`cat
/proc/sys/kernel/random/uuid`).

**Хост A** (из корня репозитория):

```bash
cargo run -p peer -- 203.0.113.10:3499 203.0.113.10:8883 cert/out/ca.crt <A-guid> <B-guid>
```

**Хост B** (уже собран релизом, из корня репозитория):

```bash
./target/release/peer 203.0.113.10:3499 203.0.113.10:8883 ./ca.crt <B-guid> <A-guid>
```

Логи цветные (`env_logger`: `INFO` зелёным, `WARN` жёлтым); уровень — через
`RUST_LOG` (по умолчанию `info`). Цвет включается на терминале сам;
принудительно — `RUST_LOG_STYLE=always`, выключить — `RUST_LOG_STYLE=never`.

Ожидаемые логи (дыры открываются параллельно, обычно за секунды; номер дыры — монотонное число, не 0..9):

```
[<time> INFO  peer] my peer_id=... looking for peer_id=..., target 10 holes
[<time> INFO  peer] введите текст и нажмите Enter: он уйдёт пиру по одной из живых дыр
[<time> INFO  connection::multilink] состояние соединения: rendezvous
[<time> INFO  connection::p2p::mqtt] рандеву (MQTT): подключено к <ip>:8883
[<time> INFO  connection::multilink] состояние соединения: rendezvous -> punching
[<time> INFO  connection::p2p] дыра <id>: пробив <low>..=<high> на <ip> (STUN-порт пира <port>)
[<time> INFO  connection::multilink] слот <id>: дыра открыта 0.0.0.0:<lport> <-> <ip>:<rport> (живых дыр: N)
[<time> INFO  connection::multilink] состояние соединения: punching -> connected(1)
...
[<time> INFO  connection::multilink] состояние соединения: connected(9) -> connected(10)
```

Дальше набор живёт сам: дыры заменяются по сроку или потерям (`политика набора: сливаем дыру … (возраст …,
потери …)`, `слот …: просим пира слить дыру` / `пир сливает дыру (Drain)`), на их месте открываются
новые. Пир, увидев запись с неизвестным номером, открывает ответную дыру (`пир открывает дыру …,
открываем свою`). Стороны сходятся зеркально: наш `local:lport <-> peer:rport` для дыры совпадает с
`local:rport <-> peer:lport` пира. «11/10» бывает: свои дыры без ответа пира место не занимают.

## Обмен сообщениями

Наберите строку и нажмите Enter — она уйдёт пиру по одной из живых дыр.
Дыра выбирается случайно из ещё не использованных: сначала из всех живых
(например, из 10), потом из оставшихся (из 9, из 8 ...), пока не побывают все,
затем цикл начинается заново. Порядок непредсказуем, нагрузка делится поровну.
С `WRAP=1` строка уходит обёрнутой (`WrappedData` с номером клиента
`CLIENT_ID`, по умолчанию 1), принятое обёрнутое выводится как
`[#N] (обёрнуто, клиент C, seq=K) текст`.
Пустые строки игнорируются,
длина ограничена `MAX_DATA_LEN` (1400 байт). Пока живых дыр нет, `peer` пишет
`не отправлено: нет живых дыр`.

```
# у отправителя
[<time> INFO  peer] отправлено по дыре [#1]: привет
# у получателя: [#N] — номер дыры, по которой пришло
[<time> INFO  peer] [#1] привет
```

## Состояния и отладка

**Состояние соединения** (`INFO`, пишется при каждой смене; во время ротации N колеблется):

| Состояние | Значение |
|---|---|
| `rendezvous` | идёт обмен адресами (STUN, MQTT-рандеву, виртуал-брокер), пробив ещё не начался |
| `punching` | живых дыр нет, но хотя бы одна пробивается |
| `connected(N)` | живых дыр N (до `HOLES_MAX`, бывает на 1–2 больше) |

Отдельно `INFO` показывает состояние MQTT-рандеву: `рандеву (MQTT): подключено
к ...`; потеря соединения — `WARN`, дальше клиент переподключается сам
(`переподключено к ...`).

**`DEBUG`** (`RUST_LOG=peer=debug,connection=debug`): keep-alive в обе стороны
(`слот N: keep-alive отправлен/получен (seq=..)`), добавление и удаление дыры в
реестре, фазы каждого слота, публикация и приём записей рандеву, `Punch`/
`PunchAck`, `Rendezvous` по дырам, статистика, `DeleteLink`, размеры
`Data`, публичный адрес по STUN и периодическая строка `live holes`. Лучше не
включать `RUST_LOG=debug` целиком: подтянутся отладочные логи rustls и rumqttc.

## Логи: stderr и syslog

По умолчанию логи идут в stderr. С `LOG_TARGET=syslog` (в `.env` или в
окружении init-скрипта) `peer` пишет в syslog: идентификатор `peer`, PID,
приоритеты `error/warning/info/debug` (`trace` уходит как `debug`). Фильтр по
модулям тот же — `RUST_LOG`/`LOG_LEVEL`. На OpenWrt `logd` принимает syslog на
`/dev/log`, читать так:

```bash
logread -e peer          # все записи peer
logread -f -e peer       # следить
```

Так же пишет `ulog` из libubox, когда stdout не терминал. Вывод в stdout под
procd можно получить и без этого (`procd_set_param stdout 1 stderr 1`), но
syslog даёт нормальные приоритеты и тег.

## Сборка под OpenWrt

Кросс-сборка под роутеры (mipsel, Xiaomi 4C и др.) — в `../../OpenWRT/README.md`:
особенности (Tier 3, `-Z build-std`, нет 64-битных атомиков и SIMD), пошаговая
ручная сборка и скрипт `../../OpenWRT/build.sh`. Итоговый бинарник около 1.7 МБ.

## Что важно знать

- **Одной дыры хватает.** Как только жива хоть одна дыра, по ней уже можно
  гонять трафик — остальные добираются параллельно.
- **TTL сам чистит записи.** Запись дыры на брокере живёт 60 с (MQTT 5
  `message_expiry_interval`). Пока дыра не залинкована, `peer` обновляет её
  каждые 30 с; как залинковалась — перестаёт, и запись протухает сама.
  Ручной уборки (`mosquitto_pub -n -r`) больше не требуется (кроме записей с чужим GUID в тестах).
- **Обрыв → замена.** Если по дыре `keepalive_timeout` (15 с) нет пакетов от пира, она считается
  потерянной (`WARN ... дыра потеряна`), менеджер набора открывает новую: STUN → свежая сессия →
  анонс → пробив. Перезапущенный пир так и находит нас снова.
- **Окно пробива 90 с** (`HOLE_DEADLINE`), ответ пира на свою дыру ждём 15 с (`RECORD_WAIT`):
  не ответил (его набор полон или его нет) — дыру закрываем и пробуем другую.
- **Версии несовместимы с прежними** (были фиксированные слоты 0..9): обе стороны обновляем вместе.

Если оба хоста за одним NAT/шлюзом (общий внешний IP) — пробив не пройдёт из-за
отсутствия hairpin, см. `CLAUDE.md` → «Известные ограничения тестового
окружения». Для реального прогона нужны разные NAT (например, `po` ↔ `ruhor`).

## `hp-client`, `mlbench`

- `hp-client` — то же, что приложение на телефоне, на обычном Linux: дыры к роутеру или ПК и TUN
  (нужен root): `hp-client <stun> <mqtt> <ca> <мой-guid> <guid-пира>`, адрес и DNS — от сервера.
  Окружение: `TUN_NAME` (`hp1`), `TUN_MTU` (1400), `REORDER_WAIT_MS` (начальное ожидание
  буфера порядка, 30 — предел адаптации; 0 — выключить), `DATA_HOLES` (0 — данные через все дыры). Маршруты в TUN —
  отдельно. (Раньше это был мост для WireGuard на `127.0.0.1:<порт>`.)
- `mlbench` — замер MultiLink без WireGuard, см. `../../Performance.md`.

Клиент сервера с белым IP (без пробива) — отдельный крейт `../../vps-client`: это уже не P2P.

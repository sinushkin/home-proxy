# `connection` — P2P UDP hole punching с набором дыр

Библиотечный крейт: устанавливает набор из нескольких независимых UDP-дыр
между двумя пирами через STUN + MQTT-рандеву, держит их живыми и даёт слать
поверх них данные. Бинарь-обёртка — в `../peer`.

## Зачем несколько дыр

Одной дыры для связи хватает. Набор из ~10 нужен, чтобы **размазать трафик**
по многим парам «локальный ↔ удалённый адрес» и не выглядеть одним устойчивым
потоком (обфускация от DPI/ТСПУ). Поверх дыр в перспективе пойдёт
зашифрованный WireGuard (`UdpMessage.Data`), отправляемый вразнобой по разным
дырам.

## Два транспорта, намеренно разнесённые

| | MQTT (рандеву) | UDP (сама дыра) |
|---|---|---|
| Что | найти пира для **первой** дыры | пробив + keep-alive + данные + оферы остальных дыр |
| Сообщение | `Rendezvous` | `PeerMessage` (`Init`/`Lite`) |
| Через кого | брокер (`profit`) | напрямую пир ↔ пир |
| Кодек | нет (чистый protobuf) | `codec` (protobuf + XOR первых 64 байт 16-байтным вектором) |

**Виртуал-брокер.** Через MQTT договариваемся только о bootstrap-слоте (0).
Как только есть хоть одна живая дыра, адреса остальных слотов пиры обменивают
по ней напрямую (тот же `Rendezvous`, но внутри `Lite`), и `multilink` скармливает записи пира
своим слотам. Так MQTT перестаёт быть точкой отказа для 9 из 10 дыр.

## Идентификация: GUID, а не адреса

Оба пира **заранее знают GUID друг друга** (`peer_id`) — это их взаимное
«имя», отдельного общего секрета/ключа нет. GUID:
- задаёт MQTT-топики: публикуем на `home-proxy/rendezvous/{my_peer_id}/{slot}`,
  слушаем `home-proxy/rendezvous/{peer_id}/+`;
- фильтрует UDP: `receive_loop` принимает пакет, только если `from_peer_id`
  совпадает с ожидаемым `peer_id`. Это же отсеивает пакет, вернувшийся к
  своему же отправителю (hairpin NAT), и посторонних на том же IP.

Аутентификации сообщений нет: XOR — не шифр, а вектор публикуется вместе с GUID.

**XOR-вектор.** На каждую регистрацию слота владелец генерирует 16 случайных
байт (`codec::random_key`) и кладёт их в `Rendezvous.key` (MQTT для слота 0,
по дыре для остальных). Пир кодирует этим вектором всё, что шлёт владельцу, а
владелец им же декодирует входящее. Так у каждой дыры и у каждого направления
свой вектор; новая регистрация слота — новый вектор.

## Слотовая модель

Каждая дыра — «слот» `0..TARGET_LINKS-1`. У слота свой сокет (свой локальный
эндпоинт), свой STUN-эндпоинт, своя сессия (`session_id`, GUID).

**Ключевой инвариант: слот k у нас пробивается только к слоту k пира.** Это
даёт сходимость без перебора N×N — обе стороны независимо берутся за один и
тот же слот и пробивают навстречу. В живом прогоне слоты сходятся зеркально:
наш `local:lport ↔ peer:rport` для слота k совпадает с `local:rport ↔
peer:lport` пира.

`PeerLinkId` = симметричная свёртка (`link_id.rs`) двух GUID сессий (наша +
пира), одинаковая на обеих сторонах. `LinkRegistry` держит `Map<PeerLinkId,
u8>` — номер слота дыры (== `u8` в заголовке `UdpMessage.slot`, «через какую
дыру»); раз `PeerLinkId` одинаков, обе стороны присваивают дыре один номер.

## Поток (жизнь одного слота, `multilink::slot_worker`)

```
STUN(socket, все серверы) → my_endpoints (первый — основной)
     │
publish_slot(slot, session, my_endpoints)  ── MQTT, retained, TTL 60 c
     │   (обновляется каждые REPUBLISH_INTERVAL=30 c, пока не залинкован)
     ▼
ждём PeerSession по этому слоту (из потока рандеву)
     │
establish(socket, …, peer.addr)            ── UDP, окно PUNCH_WINDOW=80 c
     │   перебор портов [min..max]±margin, зигзагом от STUN-порта пира
     ▼
дыра открыта → LinkRegistry.insert(link_id, slot, sender)
     │   (republish останавливаем: залинкованы — ждём новую сессию пира)
     ▼
link.lost()  ── keepalive_timeout=15 c без пакетов от пира
     ▼
LinkRegistry.remove → новый цикл (свежая сессия, заново STUN/publish/punch)
```

Параллельно на весь набор:
- **демультиплексор** раскладывает поток записей пира по слотовым очередям;
- **одна общая keep-alive-таска** раз в 5 c шлёт `KeepAlive` по всем живым
  дырам (снимает клоны сендеров под замком, шлёт без него).

Как только жив хоть один слот — по нему уже можно гонять трафик, остальные
добираются параллельно.

## TTL и перекрытие окон

Регистрация слота публикуется по **MQTT 5** с `message_expiry_interval` =
`REGISTRATION_TTL` (60 c) — брокер сам удаляет протухшую запись, ручная
проверка возраста не нужна. Окно пробива (80 c) длиннее TTL — чтобы окна
соседних попыток перекрывались и не было провала. Пока слот не залинкован,
запись обновляется каждые 30 c (< TTL, не даёт ей протухнуть); залинковались —
перестаём, и запись исчезает сама. Дедуп записей пира по `(slot, session_id)`.

## Протокол на проводе (`proto/connection.proto`)

`Rendezvous` (только MQTT, только для bootstrap-слота): `public_ip`,
`public_port`, `peer_id`, `registered_at_unix_ms`, `session_id`, `slot`, `key` (16 байт),
`extra_endpoints` (другие внешние адреса того же сокета: разные STUN-серверы могут
видеть его по-разному, пир стучится по основному и по этим).

`PeerMessage` (только UDP, через `codec`) — oneof `body`:
- `InitMessage` — фаза пробива, полный GUID-заголовок (`session_id`,
  `from_peer_id`, `to_peer_id`, `slot`) + `Punch`/`PunchAck`. Принимается
  только с ожидаемым `from_peer_id` (отсекает hairpin-эхо и чужих).
- `Lite` — всё после установки, только `slot` (короткий заголовок →
  меньше сигнатура), принимается с любого адреса при верных слоте и векторе (адрес
  отправителя становится текущим эндпоинтом пира):
  - `KeepAlive { seq }` — держит NAT-маппинг живым (случайный период 2..10 c);
  - `Data { payload }` — нагрузка (будущий WireGuard);
  - `Stats { links: [LinkStat{slot, sent, received}] }` — статистика (раз в 10 c);
  - `DeleteLink { slot }` — команда удалить линк (пробиваем заново);
  - `WrappedData { seq, payload, client_id }` — пакет, обёрнутый роутером, с
    номером клиента (u8) (см. `router`, `server`);
  - `Rendezvous {...}` — виртуал-брокер: тот же `Rendezvous`, что ушёл бы в
    MQTT, но отправленный напрямую по этой дыре (договариваемся о других слотах
    без брокера).

## Устойчивость и здоровье дыр

- **Мусор игнорируется.** Битый/чужой protobuf → `codec::decode` даёт `Err`,
  пакет пропускается. Пакет с валидным protobuf, но чужим `from_peer_id`
  отсеивается в `receive_loop` (заодно ловит hairpin-эхо).
- **Статистика.** `LinkSender`/`receive_loop` считают отправленные/принятые
  пакеты по каждой дыре (`LinkStats`). `stats_loop` раз в 10 c шлёт пиру
  таблицу по всем дырам (по каждой живой дыре — избыточно, зато дойдёт).
- **Плохая дыра.** `control_loop` сравнивает наш «получено» по дыре с «пир
  отправил»: если при выборке ≥ `MIN_STATS_SAMPLE` дошло меньше половины —
  дыра плохая. Тогда шлём сигнал слоту пробить её заново (`request_redrop`) и
  команду `DeleteLink` пиру, чтобы он тоже сбросил свой конец. Обе стороны
  сходятся на свежей дыре.

## Карта модулей

- `link_id.rs` — `PeerLinkId` (симметричная свёртка двух сессий).
- `stun.rs` — минимальный STUN-клиент (RFC 5389, IPv4): наш публичный адрес.
  `query` ждёт ответ среди чужого трафика (на сокет слота уже стучится пир),
  `parse_servers` разбирает список `ip:порт,ip2:порт`, `describe_nat` пишет в лог,
  если серверы видят сокет по-разному (другой адрес — другой маршрут, другой порт —
  NAT с зависимостью от адресата).
- `rendezvous.rs` — MQTT 5: `connect()` → `(Registrar, поток PeerSession)`,
  `Registrar::publish_slot()` с TTL. Слои клиент → канал → `event_loop`
  расписаны в doc-комментарии `connect()`/типов.
- `port_utils.rs` — `sweep_bounds()` (диапазон) и `zigzag_ports()` (порядок);
  примеры — doc-тесты (`cargo test --doc`).
- `punch.rs` — пробив ОДНОЙ дыры: `establish()` → `PeerLink` c `PeerLinkId` и
  `LinkSender`; keep-alive снаружи. `PeerLink::lost()` — потеря по тишине.
- `multilink.rs` — менеджер набора: `MultiLink::start()`, `LinkRegistry`,
  общий keepalive, перерегистрация.
- `codec.rs` — protobuf + XOR первых 64 байт (`MASKED_PREFIX`) 16-байтным вектором (`XorKey`) для
  `PeerMessage`: этого хватает, чтобы скрыть структуру protobuf, а шифротекст WireGuard дальше
  маскировать незачем.
- `xor.rs` — сам XOR: ядра под SSE2/NEON, AVX2 и AVX-512, выбор в рантайме.
- `relay.rs` — релей роутера: пересылка пакетов между двумя `MultiLink` с
  обёрткой `WrappedData` (см. `../../router`).
- `label.rs` — метка набора дыр в логах (`[phone] `, `[server] `).
- `reorder.rs` — восстановление порядка пакетов WireGuard на приёме (см. `../../Performance.md`).
- `vps.rs` — VPS-режим: порт знакомства, случайные порты слотов (см. выше).

## VPS-режим (крейты `vps-server`, `vps-client`)

Если у сервера белый IP, пробивать ничего не нужно: нет STUN, MQTT и перебора портов
(`connection/src/vps.rs`, `Discovery::VpsServer` / `Discovery::VpsClient`).

- **Знакомство.** Клиент заранее знает `ip:порт знакомства` сервера (по умолчанию 40000).
  Раз в секунду шлёт туда свою запись `Rendezvous` слота 0, сервер отвечает своей:
  «иди на мой порт P». Обмен замаскирован XOR-вектором, выведенным из пары GUID
  (`bootstrap_key`); как и остальная маскировка, это не защита.
- **Слоты.** Каждая (пере)регистрация слота на сервере занимает случайный свободный порт
  из `VPS_PORTS` (по умолчанию 40001–49999: вместе с портом знакомства 10 000 портов),
  пробив пассивный: сервер ждёт первый валидный пакет клиента. Клиент стучится ровно в
  этот порт. Слоты 1–9 договариваются, как и в обычном режиме, через виртуал-брокер.
- **Просадки.** Та же статистика дыр: если по дыре дошло меньше половины отправленного,
  слот регистрируется заново (на сервере — на новом порту), пиру уходит `DeleteLink`, и
  клиент переходит на новый порт. Вручную: `MultiLink::move_slot(slot)`.
- **Порядок пакетов** (`reorder`) и всё остальное — как в обычном режиме.
- **Брандмауэр сервера** должен пропускать входящий UDP на порт знакомства и на весь
  `VPS_PORTS`: порты слотов случайные.
- Сервер обслуживает одного клиента (`PEER_ID`), как и обычный `server`.

Проверено: сквозной тест на loopback (`vps_server_and_client_link_all_slots_and_move_a_slot`:
10 дыр, данные в обе стороны, перенос слота) и две сетевые «машины» на одном ПК (network
namespace): 10/10 дыр, 2000 из 2000 датаграмм через мост к UDP-эхо вместо WireGuard; при
потере 90% пакетов на одном порту сервер сам перенёс слот на новый порт, клиент перешёл
(за ~10 с до срабатывания статистики потерялось 5,6% трафика). По реальной сети с белым IP
не проверялось: на доступных VPS входящий UDP на эти порты закрыт брандмауэром.

## Что ещё не сделано

Отправка данных: `Data` и `LinkRegistry` готовы, но выбор дыры вразнобой и
прокачка WireGuard — в приложении (`../../android-vpn`) и на сервере
(`../../hp-server`). При обрыве MQTT-соединения `rendezvous` переподключается сам
(пауза 2 с, подписка ставится заново), клиент не умирает. Слабое место:
пока идёт пробив, слот не переключается на более свежую запись пира; обычный
пробив не справляется с симметричным NAT (порт зависит от адресата). Ошибки — через `anyhow` (`.context(...)`).

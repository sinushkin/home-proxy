# `server` — мост «клиенты (роутера или телефона) → WireGuard»

Принимает от роутера пакеты клиентов (`WrappedData` с `client_id`) по общему
набору из 10 дыр и передаёт их WireGuard'у, а ответы WireGuard'а отправляет
роутеру обратно с тем же `client_id`. Устроен как `server-rs` ,
только клиент определяется по `client_id`, а не по `(ip, port)`.

```
router --[10 дыр, WrappedData{client_id}]--> server --127.0.0.1:<порт клиента>--> WireGuard 127.0.0.1:51820
router <--                                    server <--
```

- Для каждого нового `client_id` сервер создаёт свой локальный UDP-сокет
  `127.0.0.1:0`, «подключает» его к WireGuard и шлёт с него пакеты этого клиента.
  WireGuard видит разных клиентов как разные адреса источника и отвечает каждому
  туда, откуда пришло.
- Ответ на сокете клиента уходит роутеру (`send_wrapped(client_id, …)`) по
  случайной из живых дыр. Пакеты не от WireGuard на сокет клиента не проходят.
- Клиент, от которого нет ни пакетов, ни ответов `CLIENT_TIMEOUT_SECS` секунд
  (по умолчанию 300), удаляется; следующий пакет создаёт ему новый сокет
  (WireGuard просто увидит новый адрес).

## Прямой режим (без роутера)

`PEER_ID` — GUID пира, которого ищем: роутера (тогда пакеты приходят обёрнутыми,
`WrappedData` с `client_id`) **или самого телефона**. Обычная `Data` считается
клиентом «прямой»: сервер заводит ему свой сокет к WireGuard и отвечает тоже обычной
`Data`. Готовая схема «телефон → ПК» — `../../wireguard/README.md`.

## Запуск

`run.sh` берёт настройки из `.env` рядом с собой (образец — `.env.example`):

```bash
cp .env.example .env     # MY_ID, PEER_ID, адреса, ca.crt
./run.sh
```

| Переменная | Смысл |
|---|---|
| `STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA` | как у `peer`; `STUN_ADDR` — один или несколько серверов через запятую (`ip:порт,ip2:порт`) |
| `MY_ID`, `PEER_ID` | GUID сервера и GUID роутера (`SERVER_MY_ID` роутера — набор «server») |
| `WG_ADDR` | куда передавать пакеты, по умолчанию `127.0.0.1:51820` |
| `CLIENT_TIMEOUT_SECS` | через сколько секунд тишины клиент удаляется, 300 |
| `LOG_LEVEL`, `RUST_LOG`, `LOG_TARGET=syslog` | логи (по умолчанию INFO) |

В логах: `новый клиент N: локальный адрес 127.0.0.1:порт`, `клиент N удалён по
неактивности`, раз в минуту при изменении — `клиентов: N, дыр к роутеру: M/10`.

Пакеты по клиентам видны на `DEBUG` (`RUST_LOG=server=debug,connection=debug`).

## Проверка

Логика моста покрыта тестами (`cargo test -p server`): отдельные локальные
адреса для клиентов, возврат ответов нужному клиенту, удаление неактивных,
игнорирование чужих отправителей. Сквозная проверка с роутером и двумя
телефонами — `../router/README.md`. WireGuard в проверках заменял UDP-эхо на
`127.0.0.1:51820`; с настоящим WireGuard и мостами на телефоне связь ещё не
проверялась.

## Что важно для WireGuard

WireGuard должен слушать `WG_ADDR`, а клиенты (ключи телефонов) быть заведены как
его пиры: адрес источника для него `127.0.0.1:<порт>`, меняется при пересоздании
клиента, но WireGuard это переживает (роуминг по ключу). MTU внутри туннеля —
не больше 1368 (см. `../router/README.md`).

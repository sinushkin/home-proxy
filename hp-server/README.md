# `hp-server` — домашний ПК: дыры → TUN → интернет

Схема без роутера OpenWrt: телефон пробивается (STUN + MQTT) до ПК, `hp-server` принимает его
IP-пакеты по 10 дырам и пишет их в интерфейс TUN, ответы из TUN — обратно по дырам. В интернет
пакеты выходят через NAT подсети туннеля на этом ПК — тем же путём, что и остальной трафик ПК
(в том числе через ваш домашний VPN).

```
телефон 10.80.1.1 --[10 дыр: Ordered/Data]--> hp-server --> hp0 (10.80.0.1/16) --> NAT --> интернет
```

- TCP-пакеты приходят с номером внутри своего потока, сервер возвращает им порядок; UDP и ICMP
  отдаются сразу (`hp_tun::bridge`, `connection::reorder`).
- Пиром может быть и роутер OpenWrt с телефонами за ним: их пакеты приходят как `WrappedData`
  с `client_id`, сервер запоминает адрес источника → клиент и отвечает ему через роутер.

Раньше вместо TUN здесь был мост к WireGuard: для каждого клиента свой UDP-сокет к
`127.0.0.1:51820`, WireGuard на ПК расшифровывал и выпускал трафик. От WireGuard отказались:
содержимое и так HTTPS, повторное шифрование только тратило процессор, а на роутере MT7628
WireGuard давал 10–12 Мбит/с против 21 без него (`../Performance.md`).

Тот же код (`hp_server::{settings, Common, serve}`) — у [`../vps-server`](../vps-server/README.md):
разница только в способе встречи (там — порт знакомства на белом IP, без пробива).

## Запуск (Linux)

Нужны права root (`CAP_NET_ADMIN`) и `/dev/net/tun`. `run.sh` берёт настройки из `.env` рядом
с собой (образец — `.env.example`):

```bash
cp .env.example .env     # MY_ID, PEER_ID, адреса, ca.crt
sudo ./run.sh
```

NAT подсети туннеля наружу настраивается один раз отдельно:

```bash
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A POSTROUTING -s 10.80.0.0/16 -o <внешний интерфейс> -j MASQUERADE
```

| Переменная | Смысл |
|---|---|
| `STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA` | как у `peer`; `STUN_ADDR` — один или несколько серверов через запятую (`ip:порт,ip2:порт`) |
| `MY_ID`, `PEER_ID` | GUID ПК и GUID телефона (или роутера) |
| `TUN_ADDR` | адрес ПК в туннеле и подсеть клиентов, по умолчанию `10.80.0.1/16` |
| `PEER_<n>_MY_ID`, `PEER_<n>_PEER_ID` | несколько телефонов: пара GUID на каждый (GUID ПК у каждого свой) |
| `ADDRESS_FILE` | книга выданных адресов, по умолчанию `addresses.state` рядом с настройками |
| `DNS` | DNS для клиентов через запятую; по умолчанию — резолверы ПК из `resolv.conf`; в конце всегда 8.8.8.8, 1.1.1.1 |
| `TUN_NAME`, `TUN_MTU` | `hp0`, 1400 |
| `REORDER_WAIT_MS`, `DATA_HOLES` | начальное ожидание буфера порядка (8 мс; 0 — выключить), дыр для данных (0 — все) |
| `LOG_LEVEL`, `RUST_LOG`, `LOG_TARGET=syslog`, `LOG_FILE` | логи (по умолчанию INFO); `LOG_FILE=путь` — дописывать в файл |

`hp-server --config server.env` — то же без `run.sh` (без `--config` берётся `server.env`
рядом с бинарником; переменные окружения главнее файла, относительные пути — от каталога файла).

В приложении на телефоне: GUID телефона (`PEER_ID` здесь) и GUID ПК (`MY_ID` здесь). Адрес в
туннеле и DNS телефон получает от `hp-server`: телефоны — `10.80.1.x` и дальше, адрес закреплён
за телефоном (`addresses.state`). DNS по умолчанию — те же, что у ПК, то есть запросы телефона
идут тем же путём, что и у ПК (в том числе через домашний VPN).

## ПК с включённым VPN («любимый VPN»)

Трафик телефона на ПК должен уходить в VPN, а сами дыры и STUN — мимо него, с настоящего
домашнего адреса: иначе STUN увидит адрес VPN-сервера, телефон будет стучаться туда, и дыры не
откроются. Выключить VPN «на время пробива» не выход: дыра живёт, пока пакеты по ней идут с того
же адреса, а пробивается заново постоянно (плохая дыра, смена сети у телефона, перерегистрация
слотов). Нужно один раз настроить исключение.

**Проверить, перехватывает ли VPN** — сравнить внешний адрес по маршруту по умолчанию и через
физический интерфейс (в `hp-server` это будут два STUN-запроса — обычный сокет и привязанный к
интерфейсу; пока — руками):

```bash
curl -s https://ifconfig.me; echo                   # как видят нас по умолчанию (через VPN)
curl -s --interface eth0 https://ifconfig.me; echo  # через физический интерфейс
upnpc -s | grep ExternalIPAddress                   # внешний адрес домашнего роутера (miniupnpc)
```

Адреса разные — VPN перехватывает трафик, настоящий адрес — второй (он же должен совпасть с
внешним адресом роутера). Если одинаковы и равны адресу VPN, а роутер показывает другой — VPN
перехватывает не маршрутизацией, а политикой (IPsec по политике, прозрачный прокси,
kill switch), привязка к интерфейсу не поможет, нужно исключение ниже. Если роутер сам
показывает адрес VPN — VPN стоит на роутере, и пробив до дома невозможен без исключения на нём.

**Исключение на Linux — сами, без VPN-клиента.** Пакеты службы метим по её cgroup и отправляем
по отдельной таблице через домашний шлюз; трафик телефона пересылает ядро из `hp0` (он не
принадлежит процессу), поэтому он по-прежнему уходит в VPN. Для службы systemd
`homeproxy-server.service` (метку и таблицу выбрать свободные: `wg-quick` использует 51820):

```bash
GW=192.168.1.1 DEV=eth0                                # домашний шлюз и физический интерфейс
ip route add default via $GW dev $DEV table 200
ip rule add fwmark 0x68 lookup 200 priority 90
nft add table inet hp
nft add chain inet hp out '{ type route hook output priority mangle; }'
nft add rule inet hp out socket cgroupv2 level 2 "system.slice/homeproxy-server.service" meta mark set 0x68
sysctl -w net.ipv4.conf.$DEV.rp_filter=2               # ответы телефона приходят на eth0, а маршрут к нему — в VPN
sysctl -w net.ipv4.conf.all.src_valid_mark=1
```

`type route` в цепочке нужен, чтобы ядро пересчитало маршрут после метки. Если у VPN есть
kill switch (правила firewall, режущие всё мимо VPN), метку 0x68 надо разрешить и в них.
Проверка — тот же STUN из лога службы: адрес слота должен быть домашним. Убрать:
`nft delete table inet hp; ip rule del priority 90; ip route flush table 200`. Позже это
(или `SO_BINDTODEVICE`/`SO_MARK` на своих сокетах) сделает сам `hp-server`.

**Исключение на Windows** — настройкой VPN-клиента: раздельное туннелирование по приложениям
есть у большинства (Amnezia, многие коммерческие). Оговорка: сейчас `hp-server` на Windows
работает в WSL2, а для Windows весь трафик WSL — один поток: исключив его, мимо VPN пойдёт и
трафик телефона. Чисто это решается только нативной службой на Windows, где дыры и соединения
телефона разнесены по двум процессам (в исключения — только первый); пока не сделано.

## Проверка

Мост TUN ↔ дыры покрыт тестами `hp-tun` (`cargo test -p hp-tun`: две стороны на loopback,
вместо TUN — пары сокетов), разбор аргументов — `cargo test -p hp-server`. Тот же мост в
`vps-server` проверен вживую: роутер OpenWrt и телефон через него (`../OpenWRT/Tun.md`).
`hp-server` с телефоном на домашнем ПК в варианте с TUN ещё не проверялся.

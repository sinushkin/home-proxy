# `hp-server` — домашний ПК: дыры → TUN → интернет

Схема без роутера OpenWrt: телефон пробивается (STUN + MQTT) до ПК, `hp-server` принимает его
IP-пакеты по 10 дырам и выпускает их в интернет тем же путём, что и остальной трафик ПК (в том
числе через ваш домашний VPN). Два режима (`MODE`):

- **`tun`** (Linux, по умолчанию): пакеты пишутся в интерфейс TUN, дальше — NAT подсети туннеля
  на ПК. Нужны root и одноразовая настройка NAT.
  ```
  телефон 10.80.1.1 --[10 дыр]--> hp-server --> hp0 (10.80.0.1/16) --> NAT --> интернет
  ```
- **`netstack`** (Windows — по умолчанию, Linux — по желанию): свой сетевой стек процесса
  (`hp-netstack`). TCP- и UDP-соединения телефона завершаются в `hp-server` и открываются
  заново обычными сокетами, как у любой программы: ни TUN, ни NAT, ни прав администратора. Ping
  отвечает сам стек. Окно TCP — 64 КБ без масштабирования, поэтому одно соединение — около
  6 Мбит/с при задержке 80 мс; несколько параллельных соединений складываются.
  ```
  телефон 10.80.1.1 --[10 дыр]--> hp-server (стек) --> обычные сокеты ПК --> интернет
  ```

- TCP-пакеты приходят с номером внутри своего потока, сервер возвращает им порядок; UDP и ICMP
  отдаются сразу (`hp_tun::bridge`, `connection::reorder`).
- Пиром может быть и роутер OpenWrt с телефонами за ним: их пакеты приходят как `WrappedData`
  с `client_id`, сервер запоминает адрес источника → клиент и отвечает ему через роутер.

Раньше вместо TUN здесь был мост к WireGuard: для каждого клиента свой UDP-сокет к
`127.0.0.1:51820`, WireGuard на ПК расшифровывал и выпускал трафик. От WireGuard отказались:
содержимое и так HTTPS, повторное шифрование только тратило процессор, а на роутере MT7628
WireGuard давал 10–12 Мбит/с против 21 без него (`../Performance.md`).

**Трей и сопряжение.** `hp-server` слушает протокол управления на `127.0.0.1:47001`: трей
[`../control`](../control/README.md) (`hp-tray`, Windows и Linux) показывает состояние, телефоны,
дыры и потери и добавляет телефон по QR — служба сама заводит пару GUID и набор дыр, после
первого подключения телефон сохраняется в `peers.state`. Трею при первом запуске нужна строка
подключения — `hp-server --connection-string` (новый ключ — `--new-connection-string`,
прежние строки перестают работать сразу). Без графики — `hpctl --connect <строка> status | pair
| remove <имя>`. Служба может стартовать вообще без пиров в настройках.

Тот же код (`hp_server::{settings, Common, serve}`) — у [`../vps-server`](../vps-server/README.md):
разница только в способе встречи (там — порт знакомства на белом IP, без пробива).

## Запуск (Linux)

Нужны права root (`CAP_NET_ADMIN`) и `/dev/net/tun`. `run.sh` берёт настройки из `.env` рядом
с собой (образец — `.env.example`):

```bash
cp .env.example .env     # MY_ID, PEER_ID, адреса, ca.crt
sudo ./run.sh
```

NAT подсети туннеля наружу настраивается один раз отдельно:

```bash
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A POSTROUTING -s 10.80.0.0/16 -o <внешний интерфейс> -j MASQUERADE
```

| Переменная | Смысл |
|---|---|
| `STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA` | как у `peer`; `STUN_ADDR` — один или несколько серверов через запятую (`ip:порт,ip2:порт`) |
| `MY_ID`, `PEER_ID` | GUID ПК и GUID телефона (или роутера); можно не задавать и добавлять телефоны из трея |
| `TUN_ADDR` | адрес ПК в туннеле и подсеть клиентов, по умолчанию `10.80.0.1/16` |
| `PEER_<n>_MY_ID`, `PEER_<n>_PEER_ID` | несколько телефонов: пара GUID на каждый (GUID ПК у каждого свой) |
| `ADDRESS_FILE` | книга выданных адресов, по умолчанию `addresses.state` рядом с настройками |
| `CONTROL_ADDR` | протокол управления для трея и `hpctl`, по умолчанию `127.0.0.1:47001`; `off` — выключить |
| `CONTROL_KEY_FILE` | ключ канала управления, по умолчанию `control.key` рядом с настройками (создаётся сам, права 600) |
| `PEERS_FILE` | телефоны, сопряжённые из трея, по умолчанию `peers.state` рядом с настройками (права 600) |
| `DNS` | DNS для клиентов через запятую; по умолчанию — резолверы ПК из `resolv.conf`; в конце всегда 8.8.8.8, 1.1.1.1 |
| `MODE` | `tun` или `netstack`; по умолчанию `tun`, на Windows `netstack` |
| `BIND_ADDR` | `auto` (по умолчанию) — найти адаптер мимо VPN самому; IP-адрес адаптера; `off` — не привязывать (см. «ПК с включённым VPN») |
| `TUN_NAME`, `TUN_MTU` | `hp0`, 1400 (только `MODE=tun`) |
| `REORDER_WAIT_MS`, `DATA_HOLES` | начальное ожидание буфера порядка (30 мс — предел адаптации, `connection::reorder::MAX_WAIT`; 0 — выключить), дыр для данных (0 — все) |
| `LOG_LEVEL`, `RUST_LOG`, `LOG_TARGET=syslog`, `LOG_FILE` | логи (по умолчанию INFO); `LOG_FILE=путь` — дописывать в файл |

`hp-server --config server.env` — то же без `run.sh` (без `--config` берётся `server.env`
рядом с бинарником; переменные окружения главнее файла, относительные пути — от каталога файла).

В приложении на телефоне: GUID телефона (`PEER_ID` здесь) и GUID ПК (`MY_ID` здесь). Адрес в
туннеле и DNS телефон получает от `hp-server`: телефоны — `10.80.1.x` и дальше, адрес закреплён
за телефоном (`addresses.state`). DNS по умолчанию — те же, что у ПК, то есть запросы телефона
идут тем же путём, что и у ПК (в том числе через домашний VPN).

## ПК с включённым VPN («любимый VPN»)

Трафик телефона на ПК должен уходить в VPN, а сами дыры и STUN — мимо него, с настоящего
домашнего адреса: иначе STUN увидит адрес VPN-сервера, телефон будет стучаться туда, и дыры не
откроются. Выключить VPN «на время пробива» не выход: дыра живёт, пока пакеты по ней идут с того
же адреса, а пробивается заново постоянно (плохая дыра, смена сети у телефона, перерегистрация
слотов).

**`BIND_ADDR=auto` (по умолчанию) делает это сам.** При запуске `hp-server` шлёт STUN-запросы с
обычного сокета (маршрут по умолчанию) и с сокетов, привязанных к каждому адресу ПК, и
сравнивает ответы каждого STUN-сервера по отдельности. Если через какой-то адаптер сервер видит
другой внешний адрес (или отвечает, когда по маршруту по умолчанию молчит), значит, маршрут по
умолчанию ведёт в VPN, а этот адаптер — мимо. Тогда сокеты дыр и STUN привязываются к нему:

- на Windows — к адресу адаптера: Windows отправляет пакет с интерфейса, которому принадлежит
  адрес источника;
- на Linux — ещё и к самому интерфейсу (`SO_BINDTOIFINDEX`, прав не нужно): иначе ядро выбрало
  бы маршрут по адресу назначения, то есть VPN. Ответы пира приходят на физический интерфейс,
  хотя маршрут к нему идёт в VPN, поэтому проверка обратного пути должна быть мягкой или
  выключенной: `net.ipv4.conf.<интерфейс>.rp_filter` = 2 или 0 (1 — отбросит).

Соединения телефона это не затрагивает: в режиме `netstack` их открывают обычные сокеты
`hp-server`, в режиме `tun` их пересылает ядро — и те и другие идут маршрутом по умолчанию, в
VPN. Итог виден в логе:

```
BIND_ADDR: маршрут по умолчанию идёт через VPN (<stun1> → нет ответа, <stun2> → 198.51.100.7),
  через eth0 192.168.1.5 — мимо (<stun1> → 198.51.100.8, <stun2> → 198.51.100.7): дыры и STUN привязаны к eth0
BIND_ADDR: VPN дыры не перехватывает (...), привязка не нужна
```

Сравнивать можно только ответы одного сервера. До сервера самого VPN маршрут идёт мимо
туннеля, а домашняя сеть за серым NAT провайдера может выходить к разным серверам с разных
адресов. Поэтому `STUN_ADDR` лучше задать из двух серверов: хотя бы один — не тот хост, где
стоит VPN.

Проверка — один раз при запуске: VPN, включённый позже, потребует перезапуска `hp-server`.
Явно: `BIND_ADDR=192.168.1.5` (адрес физического адаптера; на Linux интерфейс находится по
нему) или `BIND_ADDR=off`.

**Руками** — то же сравнение:

```bash
curl -s https://ifconfig.me; echo                   # как видят нас по умолчанию (через VPN)
curl -s --interface eth0 https://ifconfig.me; echo  # через физический интерфейс
upnpc -s | grep ExternalIPAddress                   # внешний адрес домашнего роутера (miniupnpc)
```

**Когда привязка не поможет.** Бывает, что внешний адрес через все адаптеры одинаков и равен
адресу VPN, а роутер показывает другой. Тогда VPN перехватывает не маршрутизацией, а политикой
(IPsec по политике, прозрачный прокси, kill switch в firewall). Если роутер сам показывает адрес
VPN, значит, VPN стоит на роутере, и пробив до дома невозможен без исключения на нём. В первом
случае нужно исключение в самом VPN:

- **Linux — сами, без VPN-клиента.** Пакеты службы метим по её cgroup и отправляем по
  отдельной таблице через домашний шлюз. Трафик телефона в режиме `tun` пересылает ядро из
  `hp0` (он не принадлежит процессу), поэтому он по-прежнему уходит в VPN. Для службы systemd
  `homeproxy-server.service` (метку и таблицу выбрать свободные: `wg-quick` использует 51820):

  ```bash
  GW=192.168.1.1 DEV=eth0                                # домашний шлюз и физический интерфейс
  ip route add default via $GW dev $DEV table 200
  ip rule add fwmark 0x68 lookup 200 priority 90
  nft add table inet hp
  nft add chain inet hp out '{ type route hook output priority mangle; }'
  nft add rule inet hp out socket cgroupv2 level 2 "system.slice/homeproxy-server.service" meta mark set 0x68
  sysctl -w net.ipv4.conf.$DEV.rp_filter=2               # ответы телефона приходят на eth0, а маршрут к нему — в VPN
  sysctl -w net.ipv4.conf.all.src_valid_mark=1
  ```

  `type route` в цепочке нужен, чтобы ядро пересчитало маршрут после метки. Если у VPN есть
  kill switch, метку 0x68 надо разрешить и в нём. Убрать:
  `nft delete table inet hp; ip rule del priority 90; ip route flush table 200`.
- **Windows** — раздельное туннелирование по приложениям в VPN-клиенте (есть у большинства:
  Amnezia, многие коммерческие). Оговорка: в режиме `netstack` соединения телефона открывает тот
  же процесс, и исключённый из VPN `hp-server.exe` выпустит мимо VPN и их. Нужно это только
  VPN-клиентам с kill switch; обычный полный туннель (OpenVPN, WireGuard) обходится привязкой.

## Windows

Нативно, без WSL: `hp-server.exe` в режиме `netstack` (по умолчанию на Windows). Сборка — как
обычно (`cargo build --release -p hp-server`, нужен `protoc`: `set PROTOC=…\protoc.exe`),
запуск — `hp-server.exe --config server.env` (или `server.env` рядом с `.exe`). Права
администратора не нужны. Подробности и ограничения — [`../windows/README.md`](../windows/README.md).

WSL2 — запасной вариант (Linux-режим `tun` с NAT внутри WSL): [`../wsl/README.md`](../wsl/README.md).
Там автоопределение `BIND_ADDR` не поможет: для Windows весь трафик WSL — один поток, и мимо
VPN его нужно выпускать на стороне Windows.

## Проверка

Мост TUN ↔ дыры покрыт тестами `hp-tun` (`cargo test -p hp-tun`: две стороны на loopback,
вместо TUN — пары сокетов), разбор настроек и выбор адаптера — `cargo test -p hp-server`. Тот же
мост в `vps-server` проверен вживую: роутер OpenWrt и телефон через него (`../OpenWRT/Tun.md`).

Вживую:

- **Windows, `netstack`** (тестовая ВМ Windows 10 за двойным NAT, клиент — `hp-client` на VPS
  вместо телефона): клиент получил адрес и DNS,
  выход в интернет — с домашнего адреса ПК, около 6 Мбит/с на соединение.
- **Windows + полный туннель OpenVPN** (вся маршрутизация ПК в VPN): без привязки пробив не
  сходится. С привязкой к физическому адаптеру — 10 из 10 дыр за 3 с, трафик телефона выходит
  через VPN.
- **Linux + полный туннель OpenVPN** (`0/1` и `128/1` через `tun0`, канал данных VPN из
  домашней сети режет ТСПУ): с `BIND_ADDR=auto` выбран `enp1s0`, 10 из 10 дыр за 4 с; с
  `BIND_ADDR=off` за 40 с ни одной. Без VPN `auto` привязку не ставит, 10 из 10.
- **Windows без VPN** (`auto`): физический адаптер отвечает так же, как маршрут по умолчанию,
  виртуальные (Hyper-V) — «сеть недоступна», привязки нет.

Не проверено: телефон через ПК в режиме `tun`, VPN с kill switch.

# windows — домашний ПК на Windows

Основной путь — нативный `hp-server.exe` в режиме `netstack` (по умолчанию на Windows): свой
сетевой стек в процессе, соединения телефона `hp-server` открывает обычными сокетами Windows.
Трафик телефона идёт теми же маршрутами, что и у любой программы на ПК, в том числе через ваш
VPN. Не нужны ни TUN, ни NAT, ни WSL, ни права администратора.

```
телефон --[дыры]--> hp-server.exe (стек) --> сокеты Windows --> VPN ПК / домашний канал --> интернет
```

## Запуск

1. Собрать (на Windows с Rust MSVC и `protoc`):
   `set PROTOC=C:\путь\protoc.exe` и `cargo build --release -p hp-server` →
   `target\release\hp-server.exe`.
2. Рядом положить `server.env` (по образцу [`../hp-server/.env.example`](../hp-server/.env.example):
   `STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA=ca.crt`, `MY_ID`, `PEER_ID`) и `ca.crt`. `MODE` и
   `BIND_ADDR` задавать не нужно: `netstack` и `auto` по умолчанию.
3. Запустить: `hp-server.exe` (берёт `server.env` рядом с собой) или
   `hp-server.exe --config C:\путь\server.env`; лог в файл — `LOG_FILE=server.log`.

В логе: `BIND_ADDR: …` (нашёлся ли VPN и к какому адаптеру привязаны дыры), `рандеву (MQTT):
подключено`, дальше — `дыра открыта`.

**Трей.** `hp-tray.exe` (`cargo build --release -p hp-tray`). При первом запуске он попросит
строку подключения — её печатает `hp-server.exe --connection-string` (в каталоге службы);
трей хранит её в `%APPDATA%\home-proxy\tray.conf`. Значок в области уведомлений
(цвет — состояние), окно со статусом, телефонами и потерями, кнопка «Добавить телефон» — QR для
приложения на телефоне. `MY_ID`/`PEER_ID` в `server.env` тогда можно не задавать: телефоны
добавляются из трея. Подробно — [`../control/README.md`](../control/README.md).

**VPN на ПК.** Если весь трафик Windows идёт в VPN, `hp-server` сам находит физический адаптер
(сравнивает STUN по маршруту по умолчанию и с каждого адаптера) и привязывает к нему сокеты дыр.
Windows отправляет пакет с того интерфейса, которому принадлежит адрес источника, так что дыры
идут мимо VPN, а соединения телефона — через VPN. Подробно, и когда это не сработает (kill
switch, VPN по политике), — [`../hp-server/README.md`](../hp-server/README.md#пк-с-включённым-vpn-любимый-vpn).

**Ограничения:**

- Службы Windows пока нет: процесс живёт, пока открыт сеанс. Запускать через планировщик
  (`schtasks /Create /SC ONLOGON …`) или вручную. Запущенный из `ssh` процесс умирает вместе с
  сессией.
- DNS для телефона: резолверы Windows не определяются. Отдаются `DNS=` из `server.env`, а без
  него — 8.8.8.8 и 1.1.1.1 (запросы всё равно идут через сокеты ПК, то есть через его VPN).
- Скорость: окно TCP стека — 64 КБ без масштабирования, около 6 Мбит/с на одно соединение при
  задержке 80 мс (4 Мбит/с при 130 мс); браузер открывает несколько соединений, и они складываются.

**Проверено с настоящим телефоном (2026-10-10).** Windows 10 (ВМ, сборка на ней: `cargo build --release
-p hp-server`, перед синхронизацией исходников старые каталоги `src` стереть — `tar` не удаляет
устаревшие файлы), `MODE=netstack`, запуск через WMI; телефон на хотспоте iPhone: 10/10 дыр, адрес
`10.80.1.1`, пинг без потерь, TCP 4 Мбит/с одним соединением и 12 четырьмя, дыры заменяются на лету.
`LOG_FILE` пишется в UTF-8; кириллицу в консоли `ssh`/PowerShell на русской Windows показывает мусором
(кодовая страница консоли) — смотреть файл копией `scp` на Linux или `Get-Content -Encoding UTF8`.

Запасной вариант — WSL2 (`MODE=tun`, NAT внутри Linux): [`../wsl/README.md`](../wsl/README.md).

Раньше здесь была нативная служба Windows с WireGuard: `install.ps1` ставил службу, туннель
WireGuard и NAT (`New-NetNat`, а где его нет — ICS). От неё отказались вместе с WireGuard: на
Windows нет ни TUN, ни нормального NAT (на тестовой ВМ `New-NetNat` недоступен, ICS
приходилось настраивать через COM), а WireGuard лишний раз шифровал уже зашифрованный HTTPS.
Свой стек в процессе снимает обе проблемы. На той схеме с настоящим телефоном проверялось: 10 из
10 дыр, рукопожатие WireGuard через дыры, `ping 8.8.8.8` с телефона через ICS; дыры на точке
доступа iPhone в части прогонов пропадали.

## Обход VPN для STUN (WSL2)

Нужен только для `hp-server` внутри WSL2: нативный `hp-server.exe` обходит VPN сам (`BIND_ADDR`).
Если ПК выходит в интернет через VPN, STUN-запрос может уйти не тем маршрутом, каким
уходят пакеты к телефону, и телефон получит адрес, с которого дыры не открываются. WSL2 выходит
в сеть через Windows, поэтому маршрут нужен на стороне Windows. `stun-bypass.ps1` берёт
`STUN_ADDR` из `server.env` и для каждого адреса:

- если маршрут идёт через физический адаптер — ничего не делает;
- если через виртуальный (VPN и т. п.) — добавляет постоянный маршрут `<stun>/32` через шлюз
  физического адаптера.

Из PowerShell **от администратора**:

```powershell
.\stun-bypass.ps1 -EnvFile C:\путь\server.env -WhatIf   # только показать
.\stun-bypass.ps1 -EnvFile C:\путь\server.env           # применить
.\stun-bypass.ps1 -EnvFile C:\путь\server.env -Remove   # убрать свои маршруты
```

После смены сети или шлюза запустите его ещё раз. **Ограничение:** обходятся только адреса
STUN-серверов, а пакеты пробива к телефону идут по обычным маршрутам ПК. Чтобы они тоже шли
мимо VPN, нужны правила самого VPN-клиента (исключение UDP или сплит-туннель).

Проверено на тестовой ВМ (Windows 10 Pro 22H2, эмуляция VPN маршрутом `0.0.0.0/1` через
виртуальный адаптер): обнаружение, `-WhatIf`, добавление, повторный запуск, `-Remove`.

# server на Windows: что важно знать

Короткие заметки по `server.exe` как службе Windows и по тестовой Windows-ВМ. Установка по
шагам — [`../windows/README.md`](../windows/README.md), общее устройство моста —
[`README.md`](README.md).

## Сборка и служба

- Собирается на самой Windows: Rust (MSVC) и `protoc` (`PROTOC=путь\protoc.exe`, отдельной
  установки не нужно, хватит распаковки архива). `cargo build --release -p server` из корня.
- Служба `homeproxy-server`: `server install --config server.env`, `server uninstall`,
  запуск диспетчером — `--service`. Автозапуск, при сбое перезапуск через 5 с, зависит от
  туннеля `WireGuardTunnel$wghp` (ставит `install.ps1`).
- У службы нет консоли и окружения: настройки только из `server.env`, логи только в файл
  (`LOG_FILE`, путь относительно `server.env`). Ошибку запуска до поднятия логов служба
  пишет в `server-error.log` рядом с `server.env`.
- Переменная окружения главнее файла, относительные пути (`MQTT_CA`, `LOG_FILE`) считаются от
  каталога `server.env`, а не от текущего (у службы это `System32`).
- Перезагрузка ПК: служба и туннель поднимаются сами (проверено), пробив и рукопожатие
  восстанавливаются без вмешательства.

## WireGuard для Windows

- Ставится MSI (`winget install WireGuard.WireGuard`), перезагрузка не нужна. Туннель
  поднимается службой `WireGuardTunnel$<имя>` из `.conf`; имя файла = имя интерфейса (`wghp`).
- `PostUp`/`PostDown` WireGuard для Windows не исполняет, поэтому `install.ps1` их
  вырезает, а NAT и брандмауэр настраивает сам.
- WireGuard слушает `0.0.0.0:51820`, а мост стучится с `127.0.0.1`. Loopback работает
  (рукопожатие проходит), снаружи порт закрыт брандмауэром Windows (входящий UDP запрещён
  по умолчанию, разрешающего правила для WireGuard нет).
- `wghp.conf` и `server.env` лежат в `C:\ProgramData\homeproxy` с доступом только SYSTEM и
  администраторам: там приватный ключ.

## NAT для подсети туннеля

Без NAT туннель поднимается и пингуется (`ping 10.77.0.1`), но в интернет трафик
телефона не выходит, и Android пишет «нет интернета».

- **`New-NetNat`** нужен WMI-провайдер `MSFT_NetNat`. На тестовой ВМ (Windows 10 Pro 22H2)
  его нет, и он не появился ни после компонентов Containers и VirtualMachinePlatform, ни
  после `DISM /RestoreHealth`, ни после перезагрузок. `VirtualMachinePlatform` после
  перезагрузки снова оказывается «Отключен». Как выглядит сбой: `Get-NetNat` даёт «Недопустимый
  класс». Реальный путь `-Nat NetNat` на этой ВМ **не проверен**.
- **ICS** (общий доступ к интернету) работает без этого провайдера. `install.ps1` по
  умолчанию (`-Nat Auto`) берёт NetNat, а при его отсутствии ICS. Проверено на ВМ: с телефона
  через туннель проходят `ping 8.8.8.8` и `ping google.com`.
- Особенности ICS: подсеть строго `/24`; адрес ICS (`ScopeAddress` в
  `HKLM\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters`) скрипт задаёт равным адресу
  туннеля (иначе ICS перепишет его на `192.168.137.1`); на машине один ICS-канал, включённый
  общий доступ на другом подключении надо снять; на туннеле поднимается DHCP/DNS-прокси ICS.
  Настройки ICS переживают перезагрузку. `uninstall.ps1` снимает ICS и возвращает
  `192.168.137.1`.

## Особенности Windows-сокетов

- Если UDP-сокет, подключённый к `127.0.0.1:51820`, получил ICMP «порт недоступен»
  (WireGuard остановлен), следующий `recv` возвращает `ConnectionReset` (на Linux —
  `ConnectionRefused`). Раньше читатель ответов клиента из-за этого навсегда завершался;
  теперь игнорирует эти ошибки (тест `client_survives_wireguard_restart`).
- Правила брандмауэра `server.exe`: входящий UDP разрешён (`install.ps1` создаёт правило
  `homeproxy-server`).
- **Не выполняйте `netsh advfirewall ...` и не меняйте правила во время работы дыр**:
  перезагрузка правил сбрасывает UDP-состояние, и все дыры теряются.

## Перезапуски и устаревшие записи брокера

Запись слота живёт в MQTT до 60 с (TTL). Если перезапустить только одну сторону, она может
застрять на записи прошлого запуска (слот ждёт до `PUNCH_WINDOW` 80 с). Наблюдали: при
включённом VPN на телефоне после перезапуска службы на Windows обе стороны надолго
зависали, а «чистый» перезапуск (остановить телефон, перезапустить службу, подождать 60 с,
запустить телефон) помогал. Перезапускайте обе стороны вместе.

## Android-клиент

- Сохранённый в приложении WireGuard-конфиг главнее `assets/wg.conf`, а `adb install -r`
  его не стирает. Для новой пары ключей передавайте `--es wgConfigB64 $(base64 -w0 client.conf)`.
- Приложение исключено из собственного туннеля, поэтому дыры и STUN идут мимо VPN.
- Запуск: сначала дыры, VPN включается, как только есть хотя бы одна живая дыра.

## Что не подтверждено

- **Нестабильные дыры на точке доступа iPhone.** Часть прогонов: 10 из 10 дыр держатся, ping
  туннеля и интернета проходит. В других дыры разом пропадают и у телефона, и у Windows
  (иногда остаётся слот 0, «мигающий» каждые 15 с) или трафик идёт в одну сторону:
  `wg show wghp` показывает растущий приём и почти нулевую отправку. Это симметричный NAT
  (`wireguard/README.md`, п. 7), корень проблемы не в службе. Проверять на обычном Wi-Fi
  с cone NAT.
- Вероятная причина части потерь дыр найдена в `punch.rs`: `Lite` принимался только с последнего
  адреса, приславшего `Init`, а слали мы на первый; при симметричном NAT пира они расходились,
  и через 15 с дыра «терялась». Исправлено (любой валидный пакет с нашим слотом переносит
  эндпоинт, как роуминг WireGuard), покрыто тестами на loopback, **на реальной сети ещё не
  проверено** (точка доступа была недоступна).
- Ответы `server` уходят в случайную живую дыру. Если одна сторона считает дыру живой, а
  другая уже нет, часть ответов теряется. Возможное улучшение: отвечать в дыру, по которой
  недавно пришёл пакет клиента.
- `stun-bypass.ps1` обходит VPN только для адресов STUN, но не для пакетов пробива.

## Тестовая ВМ `win`

- libvirt-ВМ (`rudesktop-win`) на этом ПК, SSH-алиас `win` (ключ добавлен в
  `C:\ProgramData\ssh\administrators_authorized_keys`), оболочка `cmd`.
- PowerShell-скрипты запускайте как `-File` (передача многострочных блоков через stdin
  ломается), вывод в CP866: `| iconv -f cp866 -t utf-8`. Свои `.ps1` с кириллицей сохраняйте
  в UTF-8 **с BOM**, иначе PowerShell 5.1 читает их как ANSI.
- Исходники синхронизируем `tar` через ssh в `C:\Users\user\home-proxy`, собираем там.
  Пара GUID и ключей для тестов — `WG_OUT_DIR=out/win ./gen.sh` (`wireguard/out/win/`).
- Первая перезагрузка после включения компонентов Windows идёт до нескольких минут
  (установка обновлений), ВМ в это время не отвечает по SSH.

# control — управление home-proxy: трей, сопряжение по QR

**Статус: описание. Кода пока нет.** Здесь зафиксирован замысел, чтобы `hp-server`, `hp-router`,
трей и Android-приложение сходились на одном протоколе.

`control/` (трей-приложение) лежит на одном уровне с `hp-server` и `hp-router`, а не внутри них:
службы остаются самостоятельными, их можно настраивать вручную (`server.env`, `router.env`) и
запускать вообще без `control`. Связь между ними одна: TCP-протокол управления (ниже).

## Что это

- **Протокол управления** — «пульт» службы: статус дыр, события, свои GUID, смена пира,
  перезапуск.
- **Трей-приложение** (Windows, Linux) на Slint: значок в области уведомлений, окно с
  состоянием и **показом QR-кода** для сопряжения.
- **Сопряжение с Android**: телефон сканирует QR и получает всё нужное (GUID'ы, адреса
  STUN/MQTT, адрес в туннеле) без `adb` и ручного ввода.

## Протокол: тот же protobuf, но без шифрования

Кадр: `u32` (big-endian, длина) + protobuf `ControlMessage` (`oneof`). Используется тот же
`prost`, что и в `connection` (новых зависимостей на роутере нет; на OpenWrt каждый
килобайт на счету).

**Чем отличается от протокола дыр (`PeerMessage`).** Там поверх protobuf идёт XOR
циклическим вектором: это маскировка от DPI на пути через интернет. Здесь XOR нет: канал
работает в **«демилитаризованной зоне»**, то есть только между доверенными узлами и не
выходит в интернет. Маскировать нечего, а слой XOR дал бы лишь ложное чувство защиты.

Что считается «DMZ» — на какой адрес слушает служба (`CONTROL_ADDR`):

| Где | Адрес | Замечание |
|---|---|---|
| ПК, `hp-server` и трей на одной машине | `127.0.0.1:47001` | по умолчанию |
| Windows-трей + `hp-server` в WSL2 | `127.0.0.1:47001` | WSL2 пробрасывает localhost, см. ниже |
| Роутер с OpenWrt | адрес LAN-интерфейса, например `192.168.1.1:47001` | **не** `0.0.0.0` и не WAN |

Пробрасывать unix-сокет из WSL не нужно: TCP на loopback одинаков во всех случаях, в
трее меняется только адрес.

**Защита.** Шифрования нет, поэтому:
- слушаем только нужный интерфейс, не `0.0.0.0`; на роутере правило брандмауэра тоже
  запрещает порт из WAN;
- первое сообщение соединения — `Hello { token }` (токен генерирует служба при первом
  запуске и хранит рядом с настройками); без верного токена соединение закрывается;
- токен не пишем в логи; сравнение в постоянном времени;
- в LAN трафик управления виден другим узлам, поэтому сегмент должен быть доверенным. Если
  понадобится иное, поверх добавляется TLS, формат сообщений не меняется.

### Сообщения (эскиз)

```proto
message ControlMessage {
  oneof body {
    Hello        hello         = 1;   // token, версия протокола
    GetStatus    get_status    = 2;
    Status       status        = 3;   // состояние (rendezvous/punching/connected), дыры n/10, клиенты
    Subscribe    subscribe     = 4;   // присылать события
    Event        event         = 5;   // дыра открыта/потеряна, смена эндпоинта пира, ошибка
    GetIdentity  get_identity  = 6;   // мой GUID, GUID пира
    Identity     identity      = 7;
    SetPeer      set_peer      = 8;   // GUID пира (или пара для нового телефона)
    CreatePairing create_pairing = 9; // сгенерировать пакет сопряжения (см. ниже)
    Pairing      pairing       = 10;  // PairingBundle для QR
    Restart      restart       = 11;
  }
}
```

Соединение держится открытым: служба сама присылает `Event` после `Subscribe`. Трей не
опрашивает.

## Кто что делает

- **Служба (`hp-server` или `hp-router`, модуль `control`)** — единственный источник правды. Он:
  - при первом запуске генерирует свой GUID и токен управления и хранит их рядом с настройками;
  - по запросу трея создаёт **пакет сопряжения**: генерирует GUID телефона, выбирает ему
    адрес в туннеле, заводит его набор дыр и отдаёт `PairingBundle` (см. ниже);
  - слушает `CONTROL_ADDR` и сообщает трею статус и события (дыры, смена эндпоинта, ошибки).
- **`control/` (трей на Slint)** — тонкий клиент: подключается по TCP, получает от `hp-server`
  GUID'ы и пакет сопряжения и показывает QR. Своих ключей и GUID он не генерирует и
  ничего не хранит.

Модуль `control` в службе необязательный: включается настройкой `CONTROL_ADDR` (пусто =
выключен) и, при необходимости, фичей Cargo, чтобы сборка для роутера не тянула лишнего.
Без него `hp-server` работает как раньше и настраивается вручную. Типы протокола и кадрирование
лежат в общей библиотечной части `control` и не зависят от `hp-server`. Трей, в свою очередь, не
зависит от того, где работает `hp-server`: локально, в WSL2 или на роутере, отличается только адрес.

Принятые решения:
- **Службы в целевой схеме работают на Linux**: `hp-server` в WSL2 на ПК или на обычном Linux,
  `hp-router` на роутере с OpenWrt. Нативной службы Windows больше нет.
- **Ключей, кроме GUID, нет.** Полные GUID пары — общий секрет: из них выводятся ключи подписи
  пакетов и маскировки (`hp-backend/connection/src/auth.rs`). Поэтому GUID телефона генерирует
  служба (`Uuid::new_v4`, случайность из ОС) и отдаёт его только в пакете сопряжения.
  (Раньше в замысле были ключи WireGuard через `x25519-dalek` и `wg set` — от WireGuard
  отказались.)
- **Новый телефон — новый набор дыр:** у `hp-router` это ещё одна пара `PHONE_<n>_*` (адрес
  его адрес выдаст VPS), запускается на ходу и дописывается в `router.env`, чтобы пережить перезапуск;
  у `hp-server` — смена `PEER_ID` (один телефон на службу, как сейчас).

Открытое: `hp-server` пока держит одного пира; несколько телефонов на ПК — по образцу
`hp-router` (свой набор дыр на телефон).

## Трей на Slint

- Значок в области уведомлений: цвет по состоянию (нет связи / пробив / есть дыры).
  Трей рисует отдельный крейт (например, `tray-icon`), Slint отвечает за окно.
- Окно: состояние, число живых дыр, список телефонов, кнопка **«Добавить телефон»**.
- «Добавить телефон» показывает QR (ниже).
- Трей подключается по TCP к `CONTROL_ADDR` из своих настроек: локальный `hp-server`, служба в
  WSL2 или роутер — отличаются только адресом.

## Сопряжение: QR-код и Android

Проблема: телефон должен узнать GUID пира, а пир — GUID телефона, до первой встречи. Чтобы
не нужен был обратный канал, **пакет сопряжения целиком собирает служба**, трей получает его по
протоколу управления и показывает одним QR.

### PairingBundle (protobuf, тот же формат)

```proto
message PairingBundle {
  uint32 version        = 1;
  string pc_guid        = 2;   // GUID службы (PEER_ID у телефона)
  string phone_guid     = 3;   // сгенерирован на ПК (MY_ID у телефона)
  string stun           = 4;   // ip:порт[,ip2:порт]
  string mqtt           = 5;   // ip:порт, TLS
  bytes  mqtt_ca_pem    = 6;   // ca.crt брокера
  reserved 7;                  // было: конфиг WireGuard
  uint64 expires_unix   = 8;
}
```

Адрес в туннеле и DNS в пакет не входят: их телефон получает от сервера при подключении
(`AddressRequest`/`AddressAssign`).

Внутри лежат полные GUID пары — из них выводятся все ключи, поэтому пакет — **секрет**:
показывается только по кнопке, живёт несколько минут (`expires_unix`), после успешного
сопряжения недействителен, а служба одновременно заводит набор дыр телефона. QR не логируется
и не сохраняется на диск.

Размер: пакет ~0,8 КБ (в основном CA-сертификат) — помещается в QR (вместимость ~2,9 КБ в
бинарном режиме), кодируется в base64url.

### Показ в трее

Трей получает `PairingBundle` от `hp-server` (`CreatePairing` → `Pairing`) и строит QR (крейт `qrcode` или `fast_qr`, без сети) и рисует его в
окне Slint, с таймером до истечения.

### Сканирование на Android

- Отдельный экран «Сканировать» в `android-vpn`: камера + ZXing
  (`zxing-android-embedded`, работает без Google Play Services; альтернатива — ML Kit).
- Также deep link `homeproxy://pair?d=<base64url>`: QR можно открыть штатной камерой, а
  приложение подхватит ссылку.
- Разбор `PairingBundle` заполняет `Settings`: `myId`, `peerId`, `stun`, `mqtt`, CA (то, что
  сейчас делается аргументами `am start`).
- После сопряжения запускаются дыры, VPN включается при первой живой дыре.

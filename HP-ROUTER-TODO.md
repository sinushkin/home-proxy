# hp-router: TODO

## Пакеты телефонов мимо локальной маршрутизации (проблема)

Сейчас `hp-router` принимает пакеты телефонов по своим дырам (P2P) и **не разбирает их**: каждый
IP-пакет оборачивается в `WrappedData { client_id, seq, … }` и уходит прямо в дыры `vps-server`
(см. шапку `hp-router/src/main.rs`, `phone_to_vps`). Ответы VPS возвращаются телефону тем же путём.

Из-за этого трафик телефонов **обходит весь локальный стек роутера**:
- правила `fwmark`, таблицы маршрутов и `nftables` (`udp-direct`, `direct`, `hp_udp`, `hp_direct`
  из `openwrt-k-router/`) на него не действуют: UDP напрямую через WAN и раздельное
  туннелирование работают только для LAN-клиентов роутера;
- фаервол fw4 и NAT на роутере для телефонов не применяются, нет их conntrack-записей;
- маршруты `/1` в туннель, которые ставит `vps-client`, для телефонов тоже не работают (их пакеты
  не проходят через `hp0`).

Пока это не мешает (телефоны идут всё в VPS), но расходится с обещанным поведением: «раздельное
туннелирование и UDP напрямую — для всех устройств за роутером».

## Решение: пустить пакеты телефонов через стек роутера

Вместо прямой переправки в дыры — **прокинуть пакет телефона внутрь роутера** (как пакет из LAN),
чтобы он прошёл маршрутизацию, метки и фаервол, и уже оттуда **заново завернуть** в туннель.

Варианты реализации (пока не выбран):
1. **TUN-интерфейс телефонов.** `hp-router` создаёт (или использует) TUN и кладёт в него пакеты
   телефонов с адресом источника из своей подсети; ответы из TUN уходят обратно телефону. Пакеты
   идут по обычной маршрутизации (метки, `/1`, `direct`), а `vps-client`-часть отдаёт в туннель
   уже то, что маршрутизатор отправил в `hp0`. Сложность: две роли на одном TUN или два TUN, NAT
   для адресов телефонов.
2. **Телефоны как LAN-клиенты через veth/bridge.** Отдельный интерфейс в `br-lan` или мост, через
   который телефоны попадают в обычную пересылку роутера. Меньше кода в `hp-router`, но нужна
   настройка сети OpenWrt (`network`/`firewall` через UCI).
3. **Свой заголовок в туннеле: разбор на входе.** Туннель наш, поэтому можно не полагаться
   только на ядро. Два подварианта:
   - **3а. Разбор IP-заголовка.** `hp-router` парсит IPv4/TCP/UDP пакета телефона (разбор уже есть
     в `hp-tun/src/packet.rs`: `inspect()`, протокол, порты, `flow_hash`) и сам решает: адрес
     внутри туннельной сети — отдать в TUN сервера/соседа, иначе — отправить дальше по маршруту
     (`direct`-список, UDP-диапазоны). Нужны только пакеты, которые действительно внутренние.
   - **3б. Четыре байта префикса.** К каждому пакету в `WrappedData` добавляется 4-байтовый тег:
     класс назначения (туннель / напрямую / отбросить) и, при желании, метка правила. Принимающая
     сторона разбирает тег без парсинга IP и сразу выбирает путь. Поле в протоколе — новое
     (`optional tag` или отдельный `Lite`-вариант), старые пиры его не понимают: включать только
     при явной версии протокола.
   Плюс обоих: быстро, без лишнего прохода через ядро, пакет не теряет связь с туннелем.
   Минус (важно): решение о «напрямую» принимаем мы сами, значит правила `direct`, UDP-диапазоны и
   NAT для телефонов придётся **повторить в коде**, а не взять из fw4. Это та самая «грязь», от
   которой уходит вариант 1. Поэтому 3а/3б — это компромисс: скорость и простота за счёт дублирования
   логики. Тег 3б увеличивает пакет на 4 байта: при MTU туннеля 1400 это уменьшает полезную нагрузку
   для телефонов, MSS надо занижать на 4.

## Цена (ожидаемо)

- Скорость телефонов упадёт: каждый пакет проходит лишний проход через стек ядра роутера и обратно
  в TUN, плюс двойное оборачивание (ядро → `hp0` → дыры). Замерить на `jump1`/`jump17wan`
  до и после; ориентир — текущая загрузка LAN через туннель (около 18 Мбит/с на 4C).
- Нагрузка на CPU вырастет: MT7628 (одно ядро 580 МГц) уже на пределе при ~13–18 Мбит/с.
  Возможно, понадобится ограничить число одновременных потоков телефонов или перейти на 4A (MT7621).
- MTU: пакет телефона в TUN должен помещаться в MTU туннеля (1400), иначе дробление или ICMP
  «fragmentation needed». Согласовать MSS для телефонов (`mtu_fix` в зоне `wan` уже есть).

## Зачем (контекст)

Замеры 2026-09-28 (`Infrastructure.md`, `Performance.md`): транспорт и сервер здоровы (UDP 90 Мбит/с),
но TCP вниз (VPS → клиент) внутри туннеля бимодален: то ~55–77 Мбит/с, то 2–3. Причина не найдена;
корреляции с ожиданием буфера порядка (300/200/100/50 мс), чужим трафиком и процессором роутеров нет.
Потери и джиттер вниз выше, чем вверх; иногда входящий UDP от VPS пропадает на минуты. Владелец решил:

1. Не держать жёстко 10 слотов: набор дыр 5..10 живёт динамически — дыры стареют, заменяются
   новыми, так что ТСПУ не накапливает статистику по одной паре портов.
2. Слать пакеты **в сторону клиента дважды**: напрямую и через второй VPS (`vps-relay`); какой-нибудь
   да дойдёт.

## Решения владельца

- **Номер дыры — `u32`**, монотонный; дыра «поработала — умерла».
- **Жизненный цикл дыры**: `Warming` (прогреваем следующую) → `Active` (прогрелась — в работу) →
  `Draining` (сначала обе стороны перестают слать по ней, чуть ждут, пока дойдут последние данные) →
  `Closed`; затем открывается новая, **она может идти через релей или напрямую**.
- **Кого убирать, когда дыр больше минимума**: возраст плюс худшая по потерям (не «только возраст»).
- **Релей**: отдельная служба (`vps-relay`) на другом VPS, не на хосте `vps-server`.
- **Объём**: владелец не выбирал между «только VPS-режим» и «ещё и P2P». В плане — **только
  VPS-режим** (`vps-server` ↔ `vps-client`/`hp-router`); P2P (MQTT, ACL, виртуал-брокер, `hp-server`,
  телефон) остаётся на фиксированных слотах 0..9. Если владелец захочет P2P — отдельный этап после M9.
- Диапазон: не меньше **5** живых дыр, не больше **10**; старт сразу с 5, потом +1 каждые ~10 с.

## Дизайн

### 1. Идентификатор дыры

`pub type SlotId = u32;` в `multilink.rs`. Внутри — `u32` везде (реестр, события, отправка, статус).
Клиент выбирает идентификаторы: монотонный счётчик, старт со случайного `u32` (после перезапуска
клиента старые дыры на сервере отличаются сессией и убираются). P2P продолжает использовать значения
0..9 (`TARGET_LINKS`), тип общий.

Ограничение 64-битных атомиков: счётчики дыр — `AtomicU32`/`Mutex`.

### 2. Политика набора (`PoolPolicy`, чистая функция)

```text
struct PoolPolicy { min_active: 5, max_total: 10, add_interval: 10 с, max_age: 60..180 с (случайно на дыру),
                    warm_min: время/кол-во пакетов для «прогрелась», drain_grace: ~1,5 с,
                    bad_loss: порог потерь, bad_window: окно оценки }
fn plan(now, holes: &[HoleInfo], policy) -> Vec<Action>   // Open, Retire(id), нет действий
```

Правила (по порядку):

1. Живых+прогреваемых меньше `min_active` → открыть недостающие сразу (старт: 5 одновременно).
2. Всего меньше `max_total` и с последнего открытия прошло `add_interval` → открыть ещё одну.
3. Дыра «просрочена» (`age ≥ max_age`) — кандидат на слив; сливаем, только если есть **прогретая
   замена**, чтобы `Active` не упало ниже `min_active`.
4. Когда дыр `> min_active`: слить худшую по потерям (потери за `bad_window` в обе стороны, минимальная
   выборка `MIN_LOSS_SAMPLE`, свежие дыры — с льготой `grace`); при равных — самую старую.
5. Дыра с потерями `link_is_bad` (доставлено < 50%) — сливать сразу и открыть замену (как сейчас
   `request_redrop`).

Функция чистая (время и список дыр — параметры), покрывается таблицей тестов.

### 3. Жизненный цикл и `Drain`

```text
Warming  --(получено ≥N валидных пакетов от пира и ответ на наш keep-alive)--> Active
Active   --(policy.Retire или пир прислал Drain)--> Draining
Draining --(drain_grace без новых данных или ack)--> Closed
```

- **Отправка данных выбирает только `Active`** (`SlotPicker` по `Active` слотам); **приём — по любой
  живой** (включая `Warming` и `Draining`: последние пакеты в пути должны дойти).
- Новое сообщение `Lite.drain = Drain { slot }`: «перестаю слать по этой дыре и прошу тебя
  перестать». Получатель сразу помечает дыру `Draining` у себя (не выбирает для отправки) и отвечает
  `Drain` по той же дыре (подтверждение, идемпотентно). Оба ждут `drain_grace` (+ пока `received`
  растёт), затем закрывают: дыра уходит из реестра, сокет закрывается, сервер освобождает порт.
- Инициатор слива — любая сторона; клиент — координатор набора (открывает дыры), сервер только
  выполняет и вправе сам запросить слив плохой дыры (по входящим потерям).
- Старый `DeleteLink` остаётся для P2P и аварийных случаев (потеря дыры).

### 4. Знакомство в VPS-режиме (динамическое)

Сейчас порт знакомства без состояния: на запрос слота k — текущая запись слота k. Теперь:

- Клиент шлёт подписанный `Rendezvous { slot = H, session = C }` на порт знакомства (как сейчас) для
  **нового** `H`.
- Сервер, получив `H`, которого нет: занимает случайный порт из `VPS_PORTS`, создаёт `ServerHole(H)`
  (ждёт пакеты клиента на порту, пассивно, как `ServerSlot` сейчас), отвечает `record(H, S, порт)`.
  Повторные запросы того же `H` с той же `C` — тот же ответ. `H` с другой `C` (клиент перезапустился) —
  старые дыры этого пира закрываются.
- Не подключившаяся за `PUNCH_WINDOW` (80 с) `ServerHole` закрывается; предел одновременных дыр на
  клиента `2 × max_total` (защита от переполнения таблицы).
- Таблица `offers` — `HashMap<SlotId, Rendezvous>` под мьютексом вместо `Vec<Option<_>>` по `TARGET_LINKS`;
  `serve_bootstrap` остаётся без блокировок на пути пакета.
- `unwrap()` больше не проверяет `session.slot < TARGET_LINKS` (проверка — по политике сервера).

### 5. Дедупликация и `pid`

Чтобы «какой-нибудь да дойдёт» не давал двойных пакетов, каждый пакет вниз получает номер:

- `Lite` получает необязательное поле **`optional uint32 pid = 15`** (вне `oneof`, один байт тега `0x78`,
  дописывается после нагрузки — прост для `wire.rs`). Ставится на все нагрузочные типы (`Data`,
  `WrappedData`, `Ordered`); у служебных (`KeepAlive`, `Stats`, `Drain`…) его нет.
- Счётчик `pid` — по одному на направление в `MultiLink` (`AtomicU32`, обычный счётчик по модулю 2³²),
  ставится на уровне `MultiLink::send_*` и передаётся во **все** копии пакета (по дыре и по релею).
- Приёмник: окно дедупликации в `MultiLink`/`control_loop` **до** буфера порядка: битовая маска 4096
  (512 байт, массив на стеке/в структуре) с базой = максимальный `pid`; пакет старше окна отбрасывается,
  уже виденный отбрасывается, новый отмечается. Сравнение по модулю 2³² (wrapping).
- Пакеты без `pid` (старые пиры, служебные) не дедуплицируются.

### 6. Релей (`vps-relay`)

**Назначение**: вторая копия каждого пакета вниз идёт другим путём — через отдельный VPS.

```text
vps-server ──(FWD: копия пакета)──► vps-relay ──(пакет)──► клиент
     └──────────(обычная дыра)──────────────────────────► клиент
```

- **Крейт `vps-relay/`** (бинарь, `tokio` однопоточный, как `vps-server`), UDP-пересыльщик без
  разбора нагрузки. Настройки `relay.env`: `RELAY_BIND` (адрес:порт), `RELAY_KEYS` (список ключей
  пар, hex 32 байта; `.env` в `.gitignore`), `RUST_LOG`, `LOG_FILE`.
- **Ключ релея** выводится из секрета пары (`auth.rs`: новый вывод `PairSecret::relay_key()`), полные GUID
  на релей не попадают; печатает его `vps-server --relay-key` (по образцу `--connection-string`).
- **Пакеты релея** (подпись и маскировка как у основного протокола, ключи релея, окно повтора):
  - `HELLO` (клиент → релей, раз в 2–10 с, как keep-alive): релей запоминает адрес клиента
    (`addr` + время, TTL 30 с) для данной пары;
  - `FWD` (сервер → релей): содержит готовый **пакет для клиента** (уже подписанный и замаскированный
    ключами специальной «дыры релея» пары сервер↔клиент); релей шлёт его клиенту со своего сокета как
    есть. Релей не проверяет и не меняет внутренний пакет — только подпись `FWD` (от кого).
- **Дыра релея на клиенте**: особая `LiveLink` «только приём» (`Warming`/`Active` по общему правилу,
  в `SlotPicker` не попадает, отправка данных по ней запрещена): сокет к релею, `HELLO`, приём внутренних
  пакетов с проверкой подписи ключами «дыры релея» → `LinkEvent::Peer*` как у остальных дыр. Адрес релея
  — переменная `VPS_RELAY=ip:port` у клиента (`vps-client`, `hp-router`); позже — от сервера
  служебным сообщением.
- **Режим ×2 на сервере** (`vps-server`, переменная `RELAY_DUP`): `off` — как сейчас; `always` — каждый
  нагрузочный пакет вниз уходит дважды (дыра + релей, один `pid`); `adaptive` (позже, если получится
  быстрый алгоритм) — дублируем, только когда оценка потерь вниз выше порога.
- Предупреждение: ×2 удваивает исходящий трафик `ihor` (1 vCPU) и входящий у клиента; на MIPS-роутере
  (`jump1`, предел ~18 Мбит/с) приём ×2 сокращает пропускную способность вдвое. Поэтому включается
  явно, а `adaptive` — цель следующего этапа.

### 7. Статус и управление

`HoleStatus` (`multilink.rs`, `control.proto`) дополняется: состояние дыры (`warming`/`active`/
`draining`), возраст в секундах, `via_relay: bool`. «Дыры N/10» в логах и трее — по политике
(`active / max_total`), а не по `TARGET_LINKS`. Состояние соединения: `connected(N)` — число `Active`.

  `StateTracker::set`, `send_*` возвращают `SlotId`.
- `rendezvous.rs`: `slot: u8` → `SlotId` (топики MQTT форматируют число как есть; проверка `u8::try_from`
  заменяется проверкой `< TARGET_LINKS as SlotId` для P2P).
- Потребители: `hp-server`, `hp-router` (`u32::from(h.slot)` продолжит компилироваться), `peer`,
  `mlbench`, `hp-client`, `android-lib`, трей.
- **Проверка**: `cargo build --workspace`, `cargo test --workspace` без изменения поведения; сборка
  `OpenWRT/build.sh` (нет 64-битных атомиков).

### M2. Протокол и `wire.rs`

- `connection.proto`: `Lite.pid = 15` (optional), `Drain { uint32 slot = 1 }` как `Lite.drain = 11`,
  `HoleState` при необходимости для `Stats` (или отдельно). Новые номера полей — свободные (в `Lite`
  заняты 1–10).
- `wire.rs`: `encode_data/wrapped/ordered` принимают `pid: Option<u32>`; разбор возвращает `pid`.
  Тесты «байт-в-байт с prost» для всех комбинаций (с `pid`, без, разные размеры).
- `LinkEvent::Peer*` несут `pid: Option<u32>`.

### M3. Дедупликация

- `dedup.rs`: `struct DedupWindow` (битовая маска 4096 на `[u32; 128]` — 32-битные слова), метод
  `fn seen(&mut self, pid: u32) -> bool` (первый раз — `false` и отметить). Тесты: порядок, дубликаты,
  окно, перескок через 2³², старше окна.
- `MultiLink`: счётчик `pid` (`AtomicU32`), передача в `LinkSender::send_*`; в `control_loop` — проверка
  окна до `deliver`; статистика `deduplicated` в лог `порядок пакетов`.
- Пока нет релея, `pid` ставится, только если включён `dup` (иначе `None`, поведение прежнее).

### M4. Политика набора

- `holes.rs` (новый): `HoleInfo { id, age, state, loss_in, loss_out, sample }`, `PoolPolicy`,
  `fn plan(...) -> Vec<Action>`; генератор случайного `max_age` — `XorShift32` (как `SlotPicker`).
- Тесты: старт открывает 5; +1 по интервалу до 10; при 11 уходит худшая по потерям, при равных —
  старшая; просроченная дыра сливается только при прогретой замене; ниже `min_active` не опускаемся;
  дыра `link_is_bad` сливается сразу.

### M5. VPS-режим: динамические слоты

- Сервер (`vps.rs`): `offers: Mutex<HashMap<SlotId, Rendezvous>>`, `ServerHole` (из `ServerSlot`, без
  цикла по фиксированному k: одна жизнь дыры), `Drain` от клиента → слив, освобождение порта.
- Клиент: `HoleManager` (`holes.rs`) держит `plan()`, открывает дыры (`ClientHole` — из `ClientSlot`,
  без вечного цикла: одна жизнь), прогрев (`Warming` → `Active`), слив (`Drain`).
- `MultiLink`: реестр знает состояние дыры; выбор для отправки — только `Active`; приём — любая.
- `Discovery::VpsClient`/`VpsServer` получают `PoolPolicy` через `MultiLinkOptions`.
- Проверка: тесты на loopback (сервер + клиент в одном процессе, `127.0.0.1`): 5 дыр за секунды, +1 по
  интервалу, замена дыры без потери пакетов UDP (счётчик доставки), слив по `Drain`, переживание
  перезапуска клиента.

### M6. Статус и потребители

## Риски и решения по умолчанию

- **Совместимость**: сервер и клиент обновляем вместе (динамические слоты ≥ 10 старый сервер отбрасывает
  проверкой `slot < TARGET_LINKS`). `Lite.pid` необязателен и старыми пирами игнорируется.
- **`ihor` — 1 vCPU**: ×2 удваивает работу сервера и его исходящий трафик; сначала `RELAY_DUP=off`
  для проверки динамических дыр отдельно, потом `always`.
- **Слив и данные в пути**: `drain_grace` подбирать по замеру (RTT ~90 мс: не меньше 2×RTT), приём по
  `Draining` разрешён; проверять отсутствие потерь при замене дыры (тест M5).
- **Один клиент на `vps-server`**: любой тестовый клиент занимает место `hp-router`; `jump1` отключён,
  но при возвращении он стартует сам (автозапуск службы включён) и перехватит слоты.

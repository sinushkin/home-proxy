## Зачем (контекст)

Замеры 2026-09-28 (`Infrastructure.md`, `Performance.md`): транспорт и сервер здоровы (UDP 90 Мбит/с),
но TCP вниз (VPS → клиент) внутри туннеля бимодален: то ~55–77 Мбит/с, то 2–3. Причина не найдена;
корреляции с ожиданием буфера порядка (300/200/100/50 мс), чужим трафиком и процессором роутеров нет.
Потери и джиттер вниз выше, чем вверх; иногда входящий UDP от VPS пропадает на минуты. Владелец решил:

1. Не держать жёстко 10 слотов: набор дыр 5..10 живёт динамически — дыры стареют, заменяются
   новыми, так что ТСПУ не накапливает статистику по одной паре портов.
2. Слать пакеты **в сторону клиента дважды**: напрямую и через второй VPS (`vps-relay`); какой-нибудь
   да дойдёт.

## Решения владельца

- **Номер дыры — `u32`**, монотонный; дыра «поработала — умерла».
- **Жизненный цикл дыры**: `Warming` (прогреваем следующую) → `Active` (прогрелась — в работу) →
  `Draining` (сначала обе стороны перестают слать по ней, чуть ждут, пока дойдут последние данные) →
  `Closed`; затем открывается новая, **она может идти через релей или напрямую**.
- **Кого убирать, когда дыр больше минимума**: возраст плюс худшая по потерям (не «только возраст»).
- **Релей**: отдельная служба (`vps-relay`) на другом VPS, не на хосте `vps-server`.
- **Объём**: владелец не выбирал между «только VPS-режим» и «ещё и P2P». В плане — **только
  VPS-режим** (`vps-server` ↔ `vps-client`/`hp-router`); P2P (MQTT, ACL, виртуал-брокер, `hp-server`,
  телефон) остаётся на фиксированных слотах 0..9. Если владелец захочет P2P — отдельный этап после M9.
- Диапазон: не больше **10** дыр на клиента; норма рабочего набора — **4–7** живых. Старт — с
  нижней границы нормы, потом +1 каждые ~10 с. (Значение `min_active` в `PoolPolicy` пересмотреть под 4.)
- **(2026-10-03) Ответы владельца на открытые вопросы:**
  1. Неизвестное имя и неверная подпись — сервер молчит.
  2. Клиент не ведёт таблицу портов: сокеты эфемерные, порт выбирает ОС.

## Дизайн

### 1. Идентификатор дыры

`pub type SlotId = u32;` в `multilink.rs`. Внутри — `u32` везде (реестр, события, отправка, статус).
Клиент выбирает идентификаторы: монотонный счётчик, старт со случайного `u32` (после перезапуска
клиента старые дыры на сервере отличаются сессией и убираются). P2P продолжает использовать значения
0..9 (`TARGET_LINKS`), тип общий.

Ограничение 64-битных атомиков: счётчики дыр — `AtomicU32`/`Mutex`.

### 2. Политика набора (`PoolPolicy`, чистая функция)

```text
struct PoolPolicy { min_active: 5, max_total: 10, add_interval: 10 с, max_age: 60..180 с (случайно на дыру),
                    warm_min: время/кол-во пакетов для «прогрелась», drain_grace: ~1,5 с,
                    bad_loss: порог потерь, bad_window: окно оценки }
fn plan(now, holes: &[HoleInfo], policy) -> Vec<Action>   // Open, Retire(id), нет действий
```

Правила (по порядку):

1. Живых+прогреваемых меньше `min_active` → открыть недостающие сразу (старт: 5 одновременно).
2. Всего меньше `max_total` и с последнего открытия прошло `add_interval` → открыть ещё одну.
3. Дыра «просрочена» (`age ≥ max_age`) — кандидат на слив; сливаем, только если есть **прогретая
   замена**, чтобы `Active` не упало ниже `min_active`.
4. Когда дыр `> min_active`: слить худшую по потерям (потери за `bad_window` в обе стороны, минимальная
   выборка `MIN_LOSS_SAMPLE`, свежие дыры — с льготой `grace`); при равных — самую старую.
5. Дыра с потерями `link_is_bad` (доставлено < 50%) — сливать сразу и открыть замену (как сейчас
   `request_redrop`).

Функция чистая (время и список дыр — параметры), покрывается таблицей тестов.

### 3. Жизненный цикл и `Drain`

```text
Warming  --(получено ≥N валидных пакетов от пира и ответ на наш keep-alive)--> Active
Active   --(policy.Retire или пир прислал Drain)--> Draining
Draining --(drain_grace без новых данных или ack)--> Closed
```

- **Отправка данных выбирает только `Active`** (`SlotPicker` по `Active` слотам); **приём — по любой
  живой** (включая `Warming` и `Draining`: последние пакеты в пути должны дойти). Не сделано: нет
  состояний `Warming`/`Active`/`Draining`/`Closed` у дыры в реестре вообще (M5).
- **Сообщение `Lite.drain = Drain { slot }` готово** (2026-10-02): «перестаю слать по этой дыре и
  прошу тебя перестать» — протокол, `LinkSender::send_drain`, `LinkEvent::PeerDrain`, разбор в
  `handle_lite`, round-trip проверен тестом. Получатель пока **только логирует** приход `Drain` — без
  состояния дыры (см. выше) нечего помечать `Draining`, и ответный `Drain`/ожидание `drain_grace`
  не реализованы: это сам смысл сообщения, он появится вместе с M5. Сейчас никто `Drain` не
  инициирует (нет политики, какую дыру и когда сливать — M4/M5).
- Инициатор слива — любая сторона; клиент — координатор набора (открывает дыры), сервер только
  выполняет и вправе сам запросить слив плохой дыры (по входящим потерям).
- Старый `DeleteLink` остаётся для P2P и аварийных случаев (потеря дыры).

### 4. Знакомство в VPS-режиме (динамическое + множество клиентов)

Сейчас (`hp-backend/connection/src/vps.rs`) всё заточено под ровно одного клиента: `start_server`
получает один `ServerConfig { pair: Pair, .. }` (один секрет пары) и сам занимает порт знакомства
(`UdpSocket::bind`); `serve_bootstrap` знает только эту пару и расшифровывает все пакеты её ключом.
`hp-server::Service::add()` уже умеет несколько пиров (цикл по `common.peers`, у каждого свой
`MultiLink`) — для P2P это работает, потому что там нет общего сокета, каждый пир сам ходит через
STUN. Для VPS-режима общий ресурс — **один порт знакомства на весь процесс**: если просто снять
`anyhow::ensure!(peers.len() == 1)` в `vps-server/src/main.rs`, второй пир попытается забиндить тот
же `VPS_BOOTSTRAP_PORT` второй раз и получит `EADDRINUSE`. Нужна отдельная прослойка.

**Диспетчеризация на порту знакомства — по имени в открытом виде.** Текущий пакет знакомства —
подписанная и замаскированная `Rendezvous` (сервер не может понять, какая пара, пока не расшифрует
её ключом этой самой пары — а ключ как раз и не знает, пока не определит пару). Решение: клиент
добавляет **перед** зашифрованным телом открытым текстом своё имя (`auth::peer_name` — первая
группа GUID, 8 ASCII hex-символов, фиксированная ширина). Сервер читает первые 8 байт, ищет пару по
имени в своей таблице (`HashMap<имя, Pair>`, O(1)), и только потом разбирает остаток пакета ключами
этой пары — как сейчас. Имя в открытом виде ничего не даёт постороннему (оно и так публикуется
именем в адресе/MQTT в P2P-режиме — секрет не имя, а полный GUID); подделать запись всё ещё нельзя
без секрета пары. Ответ сервера клиенту такого префикса не требует — клиент знает своего единственного
сервера и пару заранее (`vps-client`/`hp-router` настроены на одного `VPS_PUBLIC_IP`). Это только
сообщение **знакомства**; на путь данных (после пробива, `Lite`) это не распространяется.

**Владельцы состояния — задачи-акторы, без общих мьютексов (решение владельца, 2026-10-03).** У каждого
клиента свой скользящий набор дыр, поэтому его состояние (записи слотов, дыры, политика набора) живёт
только в его задаче. Общими остаются два объекта, и ни один не требует блокировки:

- `Listener` — одна задача на процесс, владеет единственным сокетом порта знакомства. Читает открытый
  префикс-имя (8 hex) и передаёт датаграмму `mpsc`-каналу нужного клиента. Таблица `имя → Sender`
  строится один раз при старте из `PEER_<n>_*` и дальше только читается (`Arc<HashMap>` без лока).
  Неизвестное имя — отбрасывается.
- `ClientActor` — одна задача на клиента. Владеет его `offers: HashMap<SlotId, Rendezvous>`, его
  дырами (`ServerHole`) и его `PoolPolicy`. Отвечает на знакомство через `Arc<UdpSocket>` того же
  порта: `send_to` берёт `&self`, блокировок не нужно.

`ServerHole` — задача одной дыры: получает от актора сессию и порт, сообщает о событиях
(`Connected`, `Lost`, `Drain`) по своему каналу, чужого состояния не видит. Порты из диапазона
общие только на уровне ОС: `bind` сам разруливает `EADDRINUSE` (как `bind_random_port`), реестра
портов нет. Список клиентов статический (`PEER_<n>_*`); «сопряжение на лету» для VPS — не в объёме
этого плана.

**Знакомство (решение владельца, 2026-10-03):** клиент шлёт запрос с открытой частью GUID (имя,
8 hex). Сервер знает имя — отвечает уже замаскированно (XOR из секрета пары, как сейчас
`bootstrap_keys`); не знает — молчит (не подтверждаем существование пары). Пробное расшифрование
по ключам всех пар не используем: имя выбирает пару за один поиск.

**Порты — общая таблица под `RwLock`.** Один реестр на процесс: битовая карта диапазона
`VPS_PORTS` (`Vec<u32>`, без 64-битных атомиков). Занять порт — взять свободный из карты под
записью (`write`), освободить — при закрытии дыры. Чтение (`read`) нужно только для статистики и
отладки. Блокировка берётся редко (открытие/закрытие дыры), на пути пакета её нет. Цель —
уменьшить коллизии: порт выбирается из свободных в карте, а не наугад с повтором `bind`; сам
`bind` всё равно нужен, потому что порт может быть занят чужой службой.
Это единственное общее изменяемое состояние на сервере; `Listener` и `ClientActor` его не трогают
напрямую, только через реестр портов.

**Дальше — как и было задумано, но на пару, а не глобально:**

- Клиент шлёт подписанный (и теперь с именем в префиксе) `Rendezvous { slot = H, session = C }` на
  порт знакомства для **нового** `H`.
- Сервер, получив `H` от известного ему (по имени) клиента, которого нет **в его собственной
  таблице `offers`**: занимает случайный порт из `VPS_PORTS` — диапазон общий на весь процесс, не
  на клиента; `bind_random_port` уже ретраит на `EADDRINUSE`, так что конкуренция портов между
  разными клиентами разруливается на уровне ОС без дополнительной координации (ёмкость: диапазон
  10 000 портов по умолчанию ÷ до 10 слотов на клиента ≈ 1000 клиентов с запасом) — создаёт
  `ServerHole(H)`, отвечает `record(H, S, порт)`. Повторные запросы той же `C` — тот же ответ. `H` с
  другой `C` — старые дыры этого (и только этого) пира закрываются.
- Не подключившаяся за `PUNCH_WINDOW` (80 с) `ServerHole` закрывается; предел одновременных дыр на
  **одного** клиента — `2 × max_total` (защита от переполнения таблицы одного пира, не влияет на
  остальных).
- Таблица `offers` — собственность `ClientActor` (`HashMap<SlotId, Rendezvous>`), а не общий
  `Arc<Mutex<Vec<Option<Rendezvous>>>>` как сейчас в `vps.rs`.
- `unwrap()` больше не проверяет `session.slot < TARGET_LINKS` (проверка — по политике сервера).
- Неизвестное имя (клиент, которого нет в `PEER_<n>_*`) — пакет молча отбрасывается, как сейчас
  отбрасывается пакет с проверкой подписи, не прошедшей для единственной известной пары.

### 5. Дедупликация и `pid`

**`Lite.pid` (поле 15) уже существует** — пришёл раньше срока вместе с модулем статистики
(`hp-stats`, см. `PLAN-ML.md`): ровно то же поле, тот же номер, та же семантика («номер пакета
вниз, общий счётчик направления в `MultiLink`, ставится на `Data`/`WrappedData`/`Ordered`»), только
сейчас он опционален и включается методом `MultiLink::attach_stats` (без вызова — всегда `None`,
нулевые накладные расходы). Для релея счётчик нужен **всегда**, когда включён релей, независимо от
`hp-stats` — а когда обе фичи понадобятся вместе, `pid` не плодить второй раз, завести общий
флаг «нумеровать пакеты» (им пользуются оба потребителя: `hp-stats`, если его `StatsHandle`
прикреплён, и дедуп/релей, если `RELAY_DUP != off`). Чтобы «какой-нибудь да дойдёт» не давал
двойных пакетов:

- Счётчик `pid` — как есть (`AtomicU32` в `MultiLink`, по модулю 2³²), ставится на уровне
  `MultiLink::send_*` и передаётся во **все** копии пакета (по дыре и по релею) — сейчас ставится,
  только когда прикреплён `hp-stats`; нужно научить ставиться и когда включён только релей, без
  статистики (M7).
- **Приёмник: окно дедупликации — сделано** (`dedup.rs`, `DedupWindow`, 2026-10-02): битовая маска
  4096 бит (`[u32; 128]`, 512 байт) с базой = максимальный виденный `pid`; пакет старше окна
  пропускается (не можем доказать, что дубль — ведём себя как раньше, до `pid`), уже виденный в
  пределах окна отбрасывается, новый отмечается. Сравнение по модулю 2³² через знаковую разность
  (`i32`), как сравнение TCP sequence numbers — перенос через 2³² не ломает порядок, пока
  расхождение меньше 2³¹. Включена в `control_loop` безусловно: срабатывает, только когда
  `pid.is_some()` (пакеты без номера — мимо, как раньше); сейчас дублей по-настоящему не бывает
  (релея нет), но проводка готова под M7 без изменений. 10 юнит-тестов (порядок, дубликат,
  вперемешку, вне окна, частичный сдвиг, перенос через 2³², большой скачок) + интеграционный тест
  через настоящий `control_loop`.
- Пакеты без `pid` (старые пиры, служебные) не дедуплицируются.

### 6. Релей (`vps-relay`)

**Назначение**: вторая копия каждого пакета вниз идёт другим путём — через отдельный VPS.

```text
vps-server ──(FWD: копия пакета)──► vps-relay ──(пакет)──► клиент
     └──────────(обычная дыра)──────────────────────────► клиент
```

- **Крейт `vps-relay/`** (бинарь, `tokio` однопоточный, как `vps-server`), UDP-пересыльщик без
  разбора нагрузки. Настройки `relay.env`: `RELAY_BIND` (адрес:порт), `RELAY_KEYS` (список ключей
  пар, hex 32 байта; `.env` в `.gitignore`), `RUST_LOG`, `LOG_FILE`.
- **Ключ релея** выводится из секрета пары (`auth.rs`: новый вывод `PairSecret::relay_key()`), полные GUID
  на релей не попадают; печатает его `vps-server --relay-key` (по образцу `--connection-string`).
- **Пакеты релея** (подпись и маскировка как у основного протокола, ключи релея, окно повтора):
  - `HELLO` (клиент → релей, раз в 2–10 с, как keep-alive): релей запоминает адрес клиента
    (`addr` + время, TTL 30 с) для данной пары;
  - `FWD` (сервер → релей): содержит готовый **пакет для клиента** (уже подписанный и замаскированный
    ключами специальной «дыры релея» пары сервер↔клиент); релей шлёт его клиенту со своего сокета как
    есть. Релей не проверяет и не меняет внутренний пакет — только подпись `FWD` (от кого).
- **Дыра релея на клиенте**: особая `LiveLink` «только приём» (`Warming`/`Active` по общему правилу,
  в `SlotPicker` не попадает, отправка данных по ней запрещена): сокет к релею, `HELLO`, приём внутренних
  пакетов с проверкой подписи ключами «дыры релея» → `LinkEvent::Peer*` как у остальных дыр. Адрес релея
  — переменная `VPS_RELAY=ip:port` у клиента (`vps-client`, `hp-router`); позже — от сервера
  служебным сообщением.
- **Режим ×2 на сервере** (`vps-server`, переменная `RELAY_DUP`): `off` — как сейчас; `always` — каждый
  нагрузочный пакет вниз уходит дважды (дыра + релей, один `pid`); `adaptive` (позже, если получится
  быстрый алгоритм) — дублируем, только когда оценка потерь вниз выше порога.
- Предупреждение: ×2 удваивает исходящий трафик `ihor` (1 vCPU) и входящий у клиента; на MIPS-роутере
  (`jump1`, предел ~18 Мбит/с) приём ×2 сокращает пропускную способность вдвое. Поэтому включается
  явно, а `adaptive` — цель следующего этапа.

### 7. Статус и управление

`HoleStatus` (`multilink.rs`, `control.proto`) дополняется: состояние дыры (`warming`/`active`/
`draining`), возраст в секундах, `via_relay: bool`. «Дыры N/10» в логах и трее — по политике
(`active / max_total`), а не по `TARGET_LINKS`. Состояние соединения: `connected(N)` — число `Active`.

### M4. Политика набора — **сделано 2026-10-02**

`connection::holes`: `HoleInfo { id, state, age, max_age, loss_out, loss_in }` (без отдельного
`sample` — как и в `multilink::loss`, «мало данных» кодируется `None`, а не числом), `PoolPolicy`,
`fn plan(holes, since_last_open, policy) -> Vec<Action>` — чистая, без сети/часов/RNG внутри.

Два уточнения дизайна, найденные при реализации (в исходном тексте раздела 2 были не до конца
определены — решения приняты и записаны прямо в коде модуля):
- **Случайный `max_age` — не внутри `plan()`**: чтобы функция оставалась чистой и детерминированной,
  каждая `HoleInfo` несёт уже назначенный при открытии `max_age` (случайным `XorShift32`
  распоряжается тот, кто создаёт дыру, — будущий `HoleManager`, M5). `plan()` только сравнивает
  `age` с готовым `max_age`.
- **«Прогретая замена» для слива просроченной — через фактический запас (`slack =
  live_count.saturating_sub(min_active)`), а не через формальное «есть ли ещё одна Warming/Active
  дыра»**: формальная проверка нашла в собственном тесте контрпример, где слив единственной
  просроченной дыры при живых ровно на `min_active` увёл бы живых ниже минимума (другие Active-дыры
  «считались» заменой, хотя сами были нужны для минимума). `slack`-подход гарантирует нижнюю
  границу по построению, а не эвристикой.

Тесты (12, все названные по-русски в терминах правил): старт открывает 5; ниже минимума — только
добор, без слива в том же цикле; рост по одной за `add_interval` до `max_total`, дальше не растёт;
при 11 дырах уходит худшая по потерям, при равных — старшая; просроченная дыра сливается, только
если это не уронит живых ниже минимума (и наоборот — остаётся, если некого терять); однозначно
плохая (`bad_loss`) сливается немедленно с открытием замены; свежая дыра (моложе `grace`) не судится
по потерям; `Warming` считается живой для минимума; `Draining` не считается живой и не трогается
повторно. Модуль пока нигде не подключён (чистая функция без потребителя) — подключение к
`MultiLink`/`vps.rs` и сам `HoleManager`, который реально открывает/сливает дыры по её решениям, —
M5.

### M5. VPS-режим: динамические слоты + множество клиентов

Два направления меняются вместе (раздел 4): динамический жизненный цикл дыры **и** то, что портом
знакомства теперь пользуются несколько независимых пар.

- `vps::Listener` (одна задача на процесс, сокет порта знакомства, диспетчеризация по имени в
  открытом префиксе, таблица `имя → mpsc::Sender` только на чтение) и `vps::ClientActor` (одна на
  клиента: `offers`, дыры, `PoolPolicy`). Создаются один раз в `vps-server`/`hp_server::serve`, а не
  внутри `MultiLink::start_discovery`: иначе второй пир попытается забиндить тот же порт повторно.
- `Discovery::VpsServer` получает канал к `ClientActor` своего пира вместо того, чтобы самому биндить
  сокет. Блокировок на пути знакомства и данных нет: только `mpsc` и `Arc<UdpSocket>`.
- Этапы внутри M5 (каждый — с зелёными тестами): **M5a** — `Listener` + `ClientActor` на сервере
  для одного клиента, поведение как сейчас, `Arc<Mutex>` из `vps.rs` удалён; **M5b** — `ClientActor`
  сам открывает/закрывает дыры по `plan()` (`ServerHole`, `Drain`), тест на loopback «один клиент»;
  **M5c** — несколько клиентов на одном `Listener`, тест «два+ клиента»; **M5d** — клиент: `HoleManager`
  (`holes.rs`) с прогревом и сливом; **M5e** — `StateTracker`/`SlotPicker` и `MultiLink` переходят
  с фиксированных `TARGET_LINKS` на динамический реестр.
- Сервер (`vps.rs`): `ServerHole` (из `ServerSlot`, без цикла по фиксированному k: одна жизнь дыры),
  `Drain` от клиента → слив, освобождение порта — на уровне одного клиента, не всего процесса.
- Клиент: `HoleManager` (`holes.rs`) держит `plan()`, открывает дыры (`ClientHole` — из `ClientSlot`,
  без вечного цикла: одна жизнь), прогрев (`Warming` → `Active`), слив (`Drain`). Клиент как был —
  один пир на процесс, множественность только на сервере.
- `MultiLink`: реестр знает состояние дыры; выбор для отправки — только `Active`; приём — любая.
- `Discovery::VpsClient`/`VpsServer` получают `PoolPolicy` через `MultiLinkOptions`.
- `vps-server/src/main.rs`: снять `anyhow::ensure!(peers.len() == 1)`, строить `SharedBootstrap`
  один раз, по одному `Discovery::VpsServer` (с общим хэндлом) на каждого пира из `PEER_<n>_*`.
- Проверка: тесты на loopback — **(а)** один клиент: 5 дыр за секунды, +1 по интервалу, замена дыры
  без потери пакетов UDP, слив по `Drain`, переживание перезапуска клиента (как было); **(б)** два+
  клиента на одном сервере одновременно: оба независимо получают свои 5..10 дыр, трафик одного не
  виден другому, рестарт/обрыв одного не трогает другого, порты не пересекаются (ёмкость диапазона —
  раздел 4).

## Риски и решения по умолчанию

- **Совместимость**: сервер и клиент обновляем вместе (динамические слоты ≥ 10 старый сервер отбрасывает
  проверкой `slot < TARGET_LINKS`). `Lite.pid` необязателен и старыми пирами игнорируется.
- **`ihor` — 1 vCPU**: ×2 удваивает работу сервера и его исходящий трафик; сначала `RELAY_DUP=off`
  для проверки динамических дыр отдельно, потом `always`.
- **Слив и данные в пути**: `drain_grace` подбирать по замеру (RTT ~90 мс: не меньше 2×RTT), приём по
  `Draining` разрешён; проверять отсутствие потерь при замене дыры (тест M5).
- **Один клиент на `vps-server` (снято решением 2026-10-02)**: было — любой тестовый клиент занимает
  место `hp-router`. После M5 (множество клиентов) это не проблема: тестовый клиент получает свою
  пару `PEER_<n>_*` и свой независимый набор дыр, не мешая `hp-router`/`jump1` при его возвращении.
  До M5 ограничение в силе — тестировать в отдельном каталоге/порту, не трогая боевую пару (как в
  `PLAN-ML.md`, живой прогон 2026-10-02).
- **Диспетчеризация по имени открытым текстом на порту знакомства**: имя — не секрет (и так
  публикуется в P2P), но стоит проверить на `ihor`, не создаёт ли открытое имя в UDP-пакете на
  характерном порту отдельный узнаваемый признак для ТСПУ (ровно то, что исследует `PLAN-ML.md`) —
  добавить в список кандидатов-признаков, когда модуль статистики подключат заново.

- **`hp-router` — композитор, а не отдельная логика.** Это `vps-client` (дыры до VPS, TUN) и

# План: модуль статистики пакетов `hp-stats` и ML-отбор дублирования

Файл нужен, чтобы работу можно было продолжить с любого места, даже в новой сессии. Перед тем как
продолжать: прочитать раздел «Как продолжить», `git status` / `git diff --stat`, чек-лист ниже. Всё,
что сделано, отмечаем в чек-листе (`[x]`) и в разделе «Журнал». Коммитить и пушить — только по
явной просьбе владельца (см. `CLAUDE.md`, правила публичного репозитория).

Дата плана: 2026-10-02.

## Зачем (контекст)

Замеры (`Performance.md`, см. `PLAN-dynamic-holes-relay.md`): TCP вниз (VPS → клиент) внутри туннеля
бимодален (то ~55–77 Мбит/с, то 2–3), потери и джиттер вниз выше, чем вверх, иногда входящий UDP от
VPS пропадает на минуты. Корреляции с буфером порядка, чужим трафиком и процессором роутеров найти
**не удалось** — не хватало данных по **отдельным** пакетам.

Задача этого модуля — собрать такие данные: **пронумеровать все пакеты вниз** (`vps-server` →
`vps-client`) и для каждого записать, дошёл он или нет, с какими параметрами уходил, сколько летел и
сколько ждал на приёме. По накопленному CSV — методами машинного обучения выяснить, фильтрует ли
ТСПУ пакеты по каким-то признакам (размер, порт, протокол внутри, темп, фаза) или потери случайны.
Если корреляция найдена — «подозрительные» пакеты дублировать: слать дважды (по второй дыре и/или
через релей `vps-relay`).

**Связь с `PLAN-dynamic-holes-relay.md`** (важно, чтобы не делать дважды):
- Номер пакета — это **тот же `Lite.pid`** (поле 15), который вводит тот план (M2/M3). Этот модуль
  его **потребитель**, а не вводит свой параллельный счётчик. Если `pid` ещё не сделан — он входит в
  объём здесь (этап S2), и тот план его переиспользует.
- «Дублировать подозрительные пакеты» — это режим **`RELAY_DUP=adaptive`** из того плана (раздел 6).
  Этот модуль даёт данные и обученное правило, по которому `adaptive` решает, кого дублировать.
- Дедупликация дублей на приёме (окно по `pid`) — из того плана (M3); здесь только используется.

## Ограничения (из `CLAUDE.md`, обязательные)

- **Никаких 64-битных атомиков** (`AtomicU64`/`AtomicI64`) ни в нашем коде, ни в зависимостях —
  MIPS32-роутеры. Счётчики — `AtomicU32` или под мьютексом. `pid` — `u32`. Время (`u64`-мс) и смещение
  часов (`i64`) — **обычные** значения под мьютексом/в одной задаче, **не атомики** (запрет — только на
  атомарные 64-битные операции, арифметика `u64`/`i64` разрешена, она уже есть в `Rendezvous`).
  Проверка — `OpenWRT/build.sh`: `undefined reference to __atomic_*_8` при линковке.
- **Сборщик CSV — только сервер**, за фичей `stats`. На роутер (`vps-client`/`hp-router`, MIPS32)
  попадает только отправка `PidReport`, обработка `TimeEcho` и `ServerTime` — они лёгкие, с
  фиксированными буферами из `pool.rs`, без 64-битных атомиков и без файлового ввода-вывода. По
  умолчанию фича выключена → в релизном бинаре роутера кода сборщика нет вовсе.
- **Канал от пути данных к сборщику — строго неблокирующий**: `mpsc::try_send`; при переполнении
  запись **отбрасывается** (считаем счётчик потерь статистики), путь данных никогда не ждёт. Сбор
  статистики не должен влиять на пропускную способность, которую он же измеряет.
- Буферы под пакеты — из банка (`pool.rs`), без выделения на пакет; `PidReport`/`TimeProbe` —
  фиксированного размера, ≤ MTU (1500).
- Зависимости — версии только в `[workspace.dependencies]`; ошибки — `anyhow`.
- Публичный репозиторий: в файлах никаких реальных IP/GUID/ключей; адреса — только документационные
  плейсхолдеры `203.0.113.10` (`profit`), `203.0.113.20` (`ruhor`), `198.51.100.7`. CSV и обученные
  модели — **в `.gitignore`** (это реальный трафик пары): добавить `stats/out/`, `*.csv.zst`.
- Тестовые прогоны — со свежими одноразовыми GUID (кроме осознанного занятия слота живого пира:
  `vps-server` обслуживает одного клиента).

## Дизайн

### 1. Крейт `hp-stats` (`hp-backend/stats/`, фича `stats`)

Отдельный библиотечный крейт в workspace; подключается `connection` как **опциональная** зависимость
за фичей `stats` (`connection/Cargo.toml`: `[features] stats = ["dep:hp-stats"]`). `vps-server`/
`hp-server` включают `connection/stats`, когда нужен сбор. Релизный роутер фичу не включает.

Содержимое крейта:
- `SentRecord` — то, что путь данных кладёт в канал при отправке пакета вниз (дёшево собрать, без
  ожидания ответа):
  ```text
  struct SentRecord {
      pid: u32,
      t_send: SystemTime,        // момент ухода с сокета (часы сервера)
      slot: SlotId,              // через какую дыру (u32, см. PLAN M1)
      via_relay: bool,
      local_port: u16,           // исходящий UDP-порт дыры (сокет сервера)
      dst_ip: IpAddr, dst_port: u16,   // текущий эндпоинт клиента (куда ушло)
      wire_len: u16,             // байт на проводе (закодированный UdpMessage)
      payload_len: u16,          // длина внутреннего IP-пакета
      inner: InnerInfo,          // proto + src/dst-порты из hp_tun::packet::PacketInfo
      kind: MsgKind,             // Data | WrappedData | Ordered
      client_id: Option<u8>,     // для WrappedData (телефон за роутером)
      flow: Option<u32>,         // корзина TCP-потока (Ordered/WrappedData)
      hole_age_ms: u32,          // возраст дыры на момент отправки (признак для ML)
      inflight: u32,             // сколько pid'ов ещё без подтверждения на момент отправки
  }
  ```
- `RecvAck` — то, что сборщику приносит разбор пришедшего `PidReport` от клиента (времена — уже в
  шкале сервера, см. §2):
  `{ pid: u32, recv_server_ms: u64, reorder_wait_ms: u16, out_of_order: bool, report_arrival: SystemTime }`.
- `ServerTime` — оценка смещения часов клиент↔сервер (см. §2), живёт на клиенте.
- `StatsHandle` — обёртка над `mpsc::Sender<StatsEvent>` (`StatsEvent = Sent(SentRecord) |
  Ack(RecvAck)`); метод `record_sent(..)`/`record_ack(..)` делает `try_send` и молча считает
  отброшенные при переполнении (`AtomicU32 dropped`). Клонируется в путь данных.
- `Collector` — задача (`spawn`), владеет pending-таблицей и писателем CSV (см. §4).

Зависимости крейта: `tokio` (канал, задача, файл), `anyhow`, `log`, разбор пакета — через `hp-tun`
(`PacketInfo`). CSV пишем **сами** (простой форматтер строки), без внешнего csv-крейта — поля
известны и фиксированы; меньше зависимостей, проще контролировать формат.

### 2. Номер пакета, обратная связь и синхронизация часов

#### 2.1. `pid`
`Lite.pid = 15` (optional uint32), общий с `PLAN-dynamic-holes-relay.md` (M2/M3). Счётчик на
направление в `MultiLink` (`AtomicU32`, по модулю 2³²), ставится в `send_*`, попадает **во все копии**
пакета (основная дыра и релей — один `pid`). Служебные пакеты (`KeepAlive`, `Stats`, `Drain`,
`PidReport`, `TimeProbe/Echo`) номера не несут.

#### 2.2. `ServerTime` — синхронизация часов в начале сессии (решение владельца)
Чтобы задержка в полёте считалась в **одних** часах (без NTP-оговорки), клиент в начале сессии
оценивает смещение своих часов относительно сервера, прогоняя несколько UDP-пакетов туда-обратно:

- `TimeProbe { client_send_ms: u64, seq: u32 }` (клиент → сервер, `Lite.time_probe = 13`).
- `TimeEcho  { client_send_ms, server_ms: u64, seq }` (сервер → клиент, `Lite.time_echo = 14`):
  сервер эхом возвращает `client_send_ms` и добавляет свои часы `server_ms` в момент ответа.
- Клиент на приёме знает `t0 = client_send_ms`, `t2 = client_recv_ms` (сейчас), `t1 = server_ms`:
  `rtt = t2 − t0`, `offset = t1 − (t0 + t2) / 2` (смещение «сервер − клиент»).
- Прогоняем ~8 проб в начале сессии, берём пробу с **минимальным `rtt`** (меньше всего влияния
  очередей — самая точная оценка). Дальше — одна проба раз ~10 с (борьба с дрейфом часов), можно
  сложить в ритм keep-alive.

`ServerTime { offset_ms: i64, best_rtt_ms: u32 }` на клиенте; метод `to_server(local: SystemTime) ->
u64` = `local_unix_ms + offset_ms`. (`i64`/`u64` — обычная арифметика, не атомики.)

**Оговорка (важно для интерпретации):** оценка `offset` из `(t0+t2)/2` предполагает симметричный путь.
Наша проблема как раз в асимметрии (вниз хуже, чем вверх), поэтому в `offset` войдёт **постоянный**
сдвиг ≈ `(задержка_вниз − задержка_вверх) / 2`. Это значит: **абсолютный** `flight_ms` может быть смещён
на эту постоянную величину, но **относительные** различия между пакетами (а именно их ищет ML:
«этот пакет летел дольше того», «на такой-то фазе задержка подскочила») от постоянного сдвига не
страдают, пока `offset` стабилен — поэтому и ресинкаем от дрейфа. Абсолютную величину при желании можно
откалибровать позже (напр. по минимуму наблюдаемого `flight_ms`).

#### 2.3. `PidReport` — обратная связь в метках времени сервера
Клиент сообщает серверу, какие `pid` он принял и когда — **в шкале сервера** (через `ServerTime`):
```text
PidReport {
    recv_base_server_ms: uint64,   // опорное время приёма, уже переведённое в часы сервера
    ack_through:         uint32,    // наибольший pid, до которого всё принято подряд
    entries: repeated {
        pid_delta:       uint32,    // pid относительно ack_through
        recv_delta_ms:   uint32,    // время приёма относительно recv_base_server_ms
        reorder_wait_ms: uint32,    // сколько пакет ждал в буфере порядка (из reorder.rs; 0 если не ждал)
        out_of_order:    bool,      // пришёл не по порядку
    }
}
```
- Клиент копит принятые `pid` в кольце фиксированного размера (время приёма + лаг из `reorder.rs`);
  раз в `STATS_REPORT_MS` (по умолчанию 50 мс) **или** при накоплении N записей шлёт `PidReport` по
  любой живой дыре вверх. `ack_through` двигает окно, чтобы `entries` не росли; если не влезают в
  MTU — режем на несколько `PidReport`.
- Лёгкая клиентская часть: кольцо на `pool.rs`-буфере, `AtomicU32`, без файлов и 64-битных атомиков —
  работает на роутере (MIPS32). За фичей — без неё клиент репорты не шлёт (трафик вверх не растёт).
- Сервер, приняв `PidReport`, уже имеет всё в своих часах: `flight_ms = recv_server_ms(pid) −
  t_send_ms(pid)` — синхронизация часов не требуется в момент сопоставления, она «вшита» в репорт.

Почему обратная связь обязательна: существующий `LinkStat {slot,sent,received}` (`stats_loop`,
раз в 10 с) даёт только **агрегат** по дыре (сколько всего потеряно), а вопрос — **какие именно**
пакеты фильтруются и с какими задержками. Это только по-пакетной обратной связью.

### 3. Тап на передаче

В `MultiLink::send_data`/`send_client`/`send_ordered` (после выбора дыры и присвоения `pid`) — под
`#[cfg(feature = "stats")]`:

```rust
#[cfg(feature = "stats")]
if let Some(h) = &self.stats {
    h.record_sent(SentRecord { pid, t_send: SystemTime::now(), slot, via_relay,
        local_port, dst_ip, dst_port, wire_len, payload_len,
        inner: hp_tun::packet::PacketInfo::parse(payload).into(), kind, client_id, flow,
        hole_age_ms, inflight });
}
```

- `local_port` — из сокета дыры (`LinkSender` знает свой сокет); `dst_ip/dst_port` — текущий эндпоинт
  пира. Оба дёшевы.
- Разбор `inner` — `hp_tun::packet` уже умеет (proto + порты); один проход по первым ~40 байтам.
- `inflight` — дешёвый `AtomicU32` в `MultiLink` (растёт на отправке, падает, когда сборщик подтвердил
  или списал — периодический снимок). Если усложняет — на первом этапе опустить, вернуть в S9.
- Всё под фичей: без `stats` ни тапа, ни поля `self.stats` нет.

Приём `PidReport`/`TimeProbe` — в `control_loop` (`multilink.rs`): распаковать, `PidReport` → для
каждой записи `stats.record_ack(..)`; `TimeProbe` (на сервере) → ответить `TimeEcho`. Под фичей.

### 4. Сборщик и CSV

Задача `Collector` (одна, `spawn` при старте сервера):
- **pending**: `HashMap<u32 /*pid*/, SentRecord>` (кольцо/лимит, чтобы не рос без предела). Обычная
  структура в одной задаче — без атомиков.
- На `StatsEvent::Sent(r)` — вставить в pending, запомнить `t_send`.
- На `StatsEvent::Ack(a)` — найти `pid`: `delivered = true`,
  `flight_ms = a.recv_server_ms − t_send_unix_ms(r)` (одни часы, через `ServerTime`),
  `ack_rtt_ms = a.report_arrival − r.t_send` (перекрёстная проверка, часов не требует),
  `recv_gap_ms` = `recv_server_ms(pid) − recv_server_ms(предыдущего по приёму pid)` (темп на приёме),
  переносим `reorder_wait_ms`/`out_of_order` из `a` → **дописать строку в CSV**, убрать из pending.
- **Тайм-аут потери**: раз в ~200 мс проходим pending; записи старше `STATS_LOSS_MS` (по умолчанию
  3000 мс, ≫ RTT) считаем `delivered = false`, пишем строку, убираем. Иначе «потерянные» не попали бы
  в CSV.
- **Запись CSV**: `BufWriter`, флаш раз в N строк/секунд. Ротация по размеру (`STATS_MAX_MB`) или по
  дате: `stats/out/down-YYYYMMDD-HHMMSS.csv`. Заголовок — в начале каждого файла.

#### Схема CSV

Одна строка — один отправленный вниз пакет (после подтверждения или тайм-аута):

| столбец | тип | смысл |
|---|---|---|
| `pid` | u32 | номер пакета (направление вниз) |
| `t_send_ms` | u64 | время отправки, unix-мс (часы сервера) |
| `delivered` | 0/1 | дошёл ли (по `PidReport`) / списан по тайм-ауту |
| `flight_ms` | i32 / пусто | время в полёте (recv_server − t_send; одни часы через `ServerTime`) |
| `ack_rtt_ms` | u32 / пусто | от отправки до прихода репорта с этим `pid` (кросс-проверка) |
| `recv_gap_ms` | u32 / пусто | **на приёме**: мс с прихода предыдущего по приёму пакета (темп/пауза) |
| `reorder_wait_ms` | u16 / пусто | **на приёме**: сколько пакет ждал в буфере порядка (из `reorder.rs`) |
| `out_of_order` | 0/1 / пусто | пришёл не по порядку |
| `slot` | u32 | через какую дыру ушёл |
| `via_relay` | 0/1 | напрямую или через релей |
| `local_port` | u16 | исходящий UDP-порт дыры (что видит ТСПУ) |
| `dst_port` | u16 | порт назначения дыры (клиент) |
| `wire_len` | u16 | размер на проводе, байт |
| `payload_len` | u16 | размер внутреннего IP-пакета |
| `inner_proto` | tcp/udp/icmp/other | протокол внутри туннеля |
| `inner_sport` | u16 / пусто | внутренний порт источника |
| `inner_dport` | u16 / пусто | внутренний порт назначения |
| `kind` | data/wrapped/ordered | тип сообщения |
| `client_id` | u8 / пусто | телефон за роутером (WrappedData) |
| `flow` | u32 / пусто | корзина TCP-потока |
| `hole_age_ms` | u32 | возраст дыры на момент отправки |
| `inflight` | u32 | неподтверждённых pid на момент отправки (признак перегруза) |
| `send_gap_us` | u32 | мкс с предыдущего пакета вниз **на отправке** (темп у источника) |

**Про «задержку/темп» (ответ на вопрос).** Есть три разных времени, не путать:
- `flight_ms` — **абсолютная** задержка конкретного пакета от сервера до клиента.
- `send_gap_us` — промежуток между соседними пакетами **у отправителя** (темп на выходе сервера).
- `recv_gap_ms` — промежуток между соседними пакетами **на приёме** (это и есть «пришёл пакет, а
  следующий — только спустя 10 мс»); + `reorder_wait_ms` отдельно ловит случай, когда пакет **ждал**
  в буфере порядка недостающего предшественника. `reorder.rs` этот лаг уже меряет (p99 отставания) —
  берём его per-packet. `dst_ip` в CSV не пишем (реальный адрес — не в репозиторий).

### 5. Включение и настройки (`vps-server`)

Переменные (`vps.env`, читаются `Settings`):
- `STATS_FILE` — каталог/префикс для CSV; пусто → сбор выключен (даже при собранной фиче).
- `STATS_REPORT_MS` (50), `STATS_LOSS_MS` (3000), `STATS_MAX_MB`, `STATS_CHAN_CAP` (напр. 4096),
  `STATS_TIMESYNC_PROBES` (8), `STATS_TIMESYNC_EVERY_S` (10).
- Сборка сбора: `cargo build -p vps-server --features connection/stats`. Без фичи — ноль накладных.
- Клиент (`vps-client`/`hp-router`) — с той же фичей (иначе нет `PidReport`/`ServerTime`, и
  `delivered`/задержки останутся пустыми). Сбор осмыслен только при фиче на **обеих** сторонах.

### 6. Офлайн-анализ и ML (этап S9)

Отдельный скрипт (`stats/analysis/`, Python; в репозиторий — **скрипт**, не данные). Данные
(`stats/out/*.csv`) — в `.gitignore`.
- Разведка: доля потерь общая и по срезам (размер-бакеты, порт, `inner_proto`, `kind`, `via_relay`,
  `hole_age`, `inflight`, темп `send_gap`/`recv_gap`, `reorder_wait`, время суток, фаза).
- Гипотезы: случайны ли потери? (χ²/взаимная информация признак↔`delivered`; автокорреляция потерь по
  `pid` — пачками или вразнобой). Отдельно — что гонит **задержку** (`flight_ms`, `reorder_wait_ms`).
- Модель: логрегрессия / градиентный бустинг (`delivered ~ признаки`), важность признаков, ROC-AUC.
  Цель — есть ли сигнал и какой признак его несёт.
- Вывод: (а) потери случайны → только «всегда ×2» на плохой фазе; (б) есть признак → правило для
  `adaptive`.

### 7. Дублирование по результату (этап S10 → `PLAN-dynamic-holes-relay.md`)

Если найден признак «пакет с вероятностью p будет отсеян» — дешёвая функция-порог в пути данных (без
ML в рантайме на 1 vCPU/MIPS) по найденным признакам (размер/порт/протокол/фаза). Это
`RELAY_DUP=adaptive` из того плана: такие пакеты уходят **дважды** (вторая дыра и/или `vps-relay`),
дубль отсеивается окном `pid` (PLAN M3). Нет сигнала → `RELAY_DUP={off,always}`; `always` надёжнее, но
удваивает трафик (на MIPS-роутере режет пропускную вдвое) — включать осознанно.

## Этапы (подробно)

### S1. Крейт `hp-stats` + канал
- `hp-backend/stats/Cargo.toml` (в `members`), типы `SentRecord`/`RecvAck`/`StatsEvent`/`MsgKind`/
  `InnerInfo`/`ServerTime`, `StatsHandle` (`try_send` + `dropped`), заготовка `Collector`.
- `connection/Cargo.toml`: `[features] stats = ["dep:hp-stats"]`, опциональная зависимость.
- Тесты: `StatsHandle` не блокирует при полном канале; форматтер строки CSV (эталоны по `kind`,
  пустые поля). Проверка: `cargo build` без фичи (крейт не линкуется), `--features connection/stats`,
  `cargo test -p hp-stats`.

### S2. Протокол: `pid` + `PidReport` + `TimeProbe`/`TimeEcho`
- `Lite.pid = 15` (если нет; как PLAN M2), `pid_report = 12`, `time_probe = 13`, `time_echo = 14`.
- `wire.rs`: разбор `pid` и новых сообщений (байт-в-байт с prost, тесты на все комбинации).
  `LinkEvent`/`control_loop` узнают их. Проверка: `cargo test -p connection wire`.

### S3. Тап на передаче
- Счётчик `pid` (`AtomicU32`), присвоение в `send_*`, передача во все копии. Под фичей —
  `self.stats: Option<StatsHandle>` и `record_sent`. `local_port`/`dst` из `LinkSender`; `inner` —
  `hp_tun::packet`. Проверка: сборка с фичей и без; loopback — `pid` монотонен, запись формируется.

### S4. `ServerTime` (синхронизация часов)
- `TimeProbe`/`TimeEcho`: сервер отвечает на пробу; клиент копит пробы, берёт min-rtt, держит
  `ServerTime {offset_ms, best_rtt_ms}`, ресинк раз в `STATS_TIMESYNC_EVERY_S`.
- Клиент штампует время приёма в шкале сервера (`to_server`). Проверка: loopback (искусственный сдвиг
  часов клиента) — `offset` оценивается с точностью ~ half-min-rtt; `flight_ms` сходится к реальной
  задержке канала теста.

### S5. Обратная связь целиком
- Клиент: кольцо принятых `pid` + `recv_server_ms` + `reorder_wait_ms`/`out_of_order` (из `reorder.rs`),
  таймер/порог, отправка `PidReport` вверх. Под фичей, MIPS-ограничения.
- Сервер: приём `PidReport` → `record_ack`. Проверка: loopback — отправленные `pid` подтверждаются,
  `flight_ms`/`recv_gap_ms`/`reorder_wait_ms` разумны; искусственный DROP → `delivered=0` по тайм-ауту;
  искусственная перестановка пакетов → `out_of_order=1` и `reorder_wait_ms>0`.

### S6. Сборщик и CSV
- pending, тайм-аут потерь, обогащение (`send_gap_us`, `recv_gap_ms`, `inflight`), `BufWriter`,
  ротация, заголовок, лог `dropped`. Проверка: интеграционный loopback с заданной долей DROP и
  перестановок — доля `delivered=0` и значения приёмных задержек в CSV совпадают с заданными (±).

### S7. Включение в `vps-server`
- `STATS_*` в `Settings`, запуск `Collector` при `STATS_FILE`, проброс `StatsHandle` в `serve`/
  `MultiLink`. Фича `stats` у `vps-server`/`vps-client`. README: `vps-server`, `vps-client`,
  `stats/README.md` (формат CSV, сборка с фичей, анализ), `CLAUDE.md` (новый крейт и фича). Проверка:
  `OpenWRT/build.sh` без фичи — нет 64-битных атомиков и кода сборщика в бинаре роутера.

### S8. Живой сбор

## Риски и решения по умолчанию

- **Нагрузка сбора искажает измерение**: канал неблокирующий (`try_send`, дроп при переполнении),
  разбор пакета дешёвый, CSV — в отдельной задаче. Контроль — счётчик `dropped`; если не ноль под
  нагрузкой, увеличить `STATS_CHAN_CAP` или упростить запись.
- **Асимметрия пути и часы**: `offset` из RTT/2 смещён на постоянную асимметрии; для **относительных**
  задержек (что ищет ML) это не мешает; ресинк от дрейфа; абсолют можно откалибровать по минимуму
  `flight_ms`. Кросс-проверка — `ack_rtt_ms` (часов не требует).
- **`PidReport`/пробы едят полосу вверх**: вверх полоса свободнее; репорт компактный и редкий (50 мс),
  пробы — 8 в начале + раз в 10 с. Потеря репорта → пакет ложно «потерян» (шум, не смещение, при объёме).
- **1 vCPU на сервере**: сбор — одна лёгкая задача; ML — офлайн; правило `adaptive` — дешёвый порог.
- **Совместимость**: `pid`/`PidReport`/`TimeProbe` — optional, старые пиры игнорируют. Без фичи у
  клиента `delivered`/задержки пусты — задокументировать.
- **Приватность**: CSV = метаданные реального трафика → `.gitignore` (`stats/out/`, `*.csv*`); в
  репозиторий — только код и скрипт анализа.

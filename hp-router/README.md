# `router` — релей телефоны ↔ сервер

Роутер держит **набор из 10 дыр к серверу** (общий, постоянный) и **по своему
набору из 10 дыр к каждому телефону**. Пакет, принятый от телефона, оборачивается
в `WrappedData` с номером этого телефона (`client_id`) и уходит серверу по одной
из дыр; ответы сервера по `client_id` возвращаются нужному телефону. WireGuard
(или другое шифрование) на роутере не нужен: содержимое пакета ему безразлично.

```
 телефон 1 <-10 дыр->\
 телефон 2 <-10 дыр->- router -<-10 дыр (общие)->  сервер --> WireGuard
 телефон n <-10 дыр->/
    Data (обычная)                                 WrappedData { client_id }
```

| Направление | Что приходит | Что делает роутер | Что уходит |
|---|---|---|---|
| телефон k → сервер | `Data` | `WrappedData { client_id: k, seq, payload }` | серверу, случайной дырой |
| сервер → телефон k | `WrappedData { client_id: k }` | по `client_id` находит телефон, разворачивает | телефону k обычной `Data`, случайной дырой |

- **`client_id`** — номер телефона, u8 (0..=255), берётся из имени переменных
  `PHONE_<n>_*` (n = 1, 2, 3 …). Сервер заводит каждому `client_id` свой
  локальный сокет к WireGuard (см. `../hp-server/README.md`).
- **`seq`** — порядковый номер пакета, отдельный счётчик на каждого клиента и
  направление; по нему получатель видит потери и перестановки между дырами.
- Дыра для каждой отправки выбирается случайно из ещё не использованных в
  цикле (`SlotPicker`): порядок непредсказуем, нагрузка делится поровну.
- Пакет от сервера без `client_id` или с неизвестным номером роутер отбрасывает
  (счётчик «потеряно»).

Сам роутер — это `connection::relay` (`forward`, `route_by_client`, `PlainOut`,
`WrappedOut`) плюс экземпляры `MultiLink` с метками `[server]`, `[phone1]`,
`[phone2]` … в логах.

## GUID

У каждой пары «два устройства» свои GUID. Роутер участвует в нескольких парах
(сервер и каждый телефон), и его GUID во всех парах **должны различаться**:
брокер различает клиентов по `client_id` (= наш GUID), одинаковые вытеснят друг
друга, а слоты одного GUID затирали бы друг друга. Роутер откажется стартовать,
если это нарушено (и если один GUID телефона указан дважды).

| Кто | Его GUID | Кого ищет |
|---|---|---|
| телефон n | `P<n>` | `R<n>` |
| роутер, набор телефона n | `R<n>` (`PHONE_<n>_MY_ID`) | `P<n>` (`PHONE_<n>_PEER_ID`) |
| роутер, набор «server» | `RS` (`SERVER_MY_ID`) | `S` (`SERVER_PEER_ID`) |
| сервер | `S` | `RS` |

## Запуск

`run.sh` берёт настройки из `.env` рядом с собой (образец — `.env.example`):

```bash
cp .env.example .env     # заполнить GUID'ы, адреса и путь к ca.crt
./run.sh                 # LOG_LEVEL=debug ./run.sh — подробнее
```

Переменные: `STUN_ADDR` (один или несколько серверов через запятую), `MQTT_ADDR`, `MQTT_CA`, `SERVER_MY_ID`,
`SERVER_PEER_ID`, для каждого телефона `PHONE_<n>_MY_ID` и `PHONE_<n>_PEER_ID`
(нумерация подряд с 1, до 255), а также `LOG_LEVEL`, `RUST_LOG`,
`LOG_TARGET=syslog` (на OpenWrt — `logread`). Без `cargo` рядом должен лежать
бинарник `./router` (и `ca.crt`, `.env`). Сборка под роутер —
`../OpenWRT/README.md`.

Во время работы роутер пишет одну строку, только когда что-то изменилось:

```
дыры: сервер 10/10, телефоны [1:10/10 2:10/10]; телефоны->сервер 6 (потеряно 0), сервер->телефоны 6 (потеряно 0)
```

«Потеряно» — пакеты, которые некуда было отправить (нет живых дыр в нужную
сторону или неизвестный `client_id`). Состояния каждого набора
(`rendezvous -> punching -> connected(N)`) — в INFO с меткой; keep-alive и
прочее — в DEBUG/TRACE.

## Как проверить руками

Телефоны и сервер можно изобразить обычными `peer`, а WireGuard — любым UDP-эхо
на `127.0.0.1:51820`. Телефон шлёт обычную `Data`, «сервер» — `peer` с
`WRAP=1 CLIENT_ID=<n>`, либо настоящий `server` (`../hp-server`):

```bash
peer <stun> <mqtt> ca.crt P1 R1        # телефон 1 (ищет R1)
peer <stun> <mqtt> ca.crt P2 R2        # телефон 2 (ищет R2)
# на сервере: ./hp-server (MY_ID=S, PEER_ID=RS) и UDP-эхо на 127.0.0.1:51820
```

Проверено вживую: два телефона (один на этой машине, второй, роутер, сервер и
UDP-эхо на `ruhor`). Все три набора собрали 10/10 дыр. Сервер завёл двум клиентам
два разных локальных сокета (`127.0.0.1:47435` и `:59459`), эхо-сервер увидел два
разных порта источника, каждый телефон получил ответы только на свои пакеты;
по 6 пакетов в каждую сторону, потерь нет.

## Ограничения и что ещё не сделано

- **Нет моста для WireGuard на телефоне.** Роутер переносит `Data`, но
  телефонный WireGuard пока не умеет отдавать пакеты в дыры: нужен локальный
  UDP-мост (слушает `127.0.0.1:порт`, кладёт датаграммы в `send_data` и
  выдаёт полученное обратно).
- **Размер пакета.** Полезная нагрузка не больше `MAX_DATA_LEN` (1400 байт).
  Пакет WireGuard длиннее вложенного IP-пакета на 32 байта (заголовок 16 +
  тег 16), значит **MTU WireGuard за роутером — не больше 1368**
  (с запасом 1360).
- **Потери и порядок не восстанавливаются**: это UDP, `seq` только даёт
  получателю знать о них.
- **Память роутера.** Каждый набор — 10 UDP-сокетов и свой MQTT-клиент; на
  MT7628 (64 МБ ОЗУ, около 20 МБ свободно) число телефонов надо подбирать
  опытом, на железе при нескольких телефонах не мерили.
- **Устаревшая регистрация.** Пока идёт пробив, слот не переключается на более
  свежую запись пира: если при старте на брокере ещё лежит retained-запись
  прошлого запуска (живёт до 60 с), слот застревает на ней до конца окна
  пробива (80 с) и лишь потом берёт новую. После аварийного перезапуска
  подождите минуту или используйте новые GUID'ы.
- Работа под нагрузкой на реальном роутере не проверялась: бинарник запускается
  на MT7628 (см. `../OpenWRT/README.md`), но тест связи с телефоном ещё
  впереди.

# Роутер OpenWrt: `hp-router` — дом через VPS и телефоны

Весь трафик LAN и Wi-Fi роутера уходит к VPS с белым IP по нашим UDP-дырам как есть, без
WireGuard; телефоны пробиваются до роутера и выходят в интернет тем же путём. Шифрования нет:
сами пакеты (HTTPS и т.п.) идут как есть, каждый пакет в дыре подписан (первые 128 байт и длина)
и его заголовок замаскирован XOR. TCP-пакеты получают номер внутри своего потока (корзина по хэшу
соединения), и получатель восстанавливает их порядок; UDP, ICMP и прочее отдаются сразу.

```
LAN-клиент -> роутер: hp0 (10.80.0.2, TUN hp-router) -> дыры (4–10) ==== интернет ====
           -> VPS: vps-server (TUN hp0, 10.80.0.1/16) -> NAT -> интернет
телефон 10.80.1.x -> P2P-дыры (4–10) -> роутер (hp-router, без TUN) -> дыры к VPS -> ...
```

Раньше здесь был WireGuard поверх `vps-client` (10–12 Мбит/с на этом роутере) — от него
отказались, см. «Скорость» ниже.

Проверено: Xiaomi Mi Router 4C (MT7628, OpenWrt 23.05.4), VPS на Debian 12, телефон Android на
LTE. Ниже `203.0.113.30` — белый IP VPS, `192.168.3.1` — шлюз роутера по WAN, LAN —
`192.168.1.0/24`.

## 1. VPS

1. Брандмауэр пропускает входящий UDP на порт знакомства и диапазон портов дыр
   (`ufw allow 40000:40999/udp`).
2. NAT для подсети туннеля наружу и пересылка:
   ```bash
   sysctl -w net.ipv4.ip_forward=1
   iptables -t nat -A POSTROUTING -s 10.80.0.0/16 -o <внешний интерфейс> -j MASQUERADE
   ```
3. `vps-server` (`../vps-server/README.md`) с `vps.env`:
   ```
   VPS_PUBLIC_IP=203.0.113.30
   VPS_PORTS=40001-40999
   MY_ID=<GUID сервера>
   PEER_ID=<GUID роутера для VPS>
   TUN_ADDR=10.80.0.1/16
   ```
   Адреса в туннеле роутеру и телефонам раздаёт сервер (книга — `addresses.state` рядом с
   `vps.env`), DNS для них — резолверы VPS или `DNS=` (в конце 8.8.8.8, 1.1.1.1).
   Запуск от root (нужен `CAP_NET_ADMIN`): при старте поднимается интерфейс `hp0`.

## 2. Роутер

1. Модуль TUN: `opkg update && opkg install kmod-tun` (появится `/dev/net/tun`).
2. `hp-router` (сборка — `README.md`, `PACKAGES=hp-router ./OpenWRT/build.sh`) и настройки
   `router.env` рядом с ним (образец — `../hp-router/router.env.example`):
   ```
   VPS_SERVER=203.0.113.30:40000
   VPS_MY_ID=<GUID роутера для VPS>
   VPS_PEER_ID=<GUID сервера>
   STUN_ADDR=203.0.113.10:3499
   MQTT_ADDR=203.0.113.10:8883
   MQTT_CA=ca.crt
   PHONE_1_MY_ID=<GUID роутера для телефона 1>
   PHONE_1_PEER_ID=<GUID телефона 1>
   ```
   Запуск в фоне:
   ```sh
   start-stop-daemon -S -b -m -p /tmp/hp/hp-router.pid -x /bin/sh -- -c \
     'cd /tmp/hp && exec ./hp-router --config /tmp/hp/router.env > /tmp/hp/hp-router.log 2>&1'
   ```
   Роутер получает от VPS адрес (`адрес в туннеле: 10.80.0.2/16`), поднимает с ним `hp0`; в
   логе — `[vps] ... connected(10)`, для телефонов — `[<имя телефона>] ...`.

   **Постоянная установка (флеш) и служба procd** — вместо `/tmp/hp`:
   ```sh
   scp -O target/openwrt/mipsel-unknown-linux-musl/release/hp-router root@<роутер>:/usr/bin/hp-router
   ssh root@<роутер> 'mkdir -p /etc/hp-router'   # сюда router.env и ca.crt
   OpenWRT/luci-app-homeproxy/install.sh root@<роутер>   # /etc/init.d/hp-router + страница LuCI
   ssh root@<роутер> '/etc/init.d/hp-router start; logread -e hp-router | tail'
   ```
   Для трея и LuCI в `router.env` — `CONTROL_ADDR=<адрес LAN>:47001` (только LAN; ключ
   `control.key` и сопряжённые из трея телефоны `phones.state` появятся рядом сами).
   Автозапуск — `/etc/init.d/hp-router enable`, но шаги 3–4 (маршрут `hp0`, firewall) служба
   пока не делает: после её запуска их нужно повторить.
3. Маршруты: default — в `hp0` (и LAN, и весь остальной трафик самого роутера), а адрес VPS и
   адрес STUN/MQTT — явными хостовыми маршрутами в обход, напрямую через реальный WAN:
   ```sh
   ip route add default via 10.80.0.1 dev hp0            # после каждого запуска hp-router (адрес — свой, TUN-адрес VPS)
   ip route add 203.0.113.30 via 192.168.3.1 dev eth0.2   # VPS — мимо hp0
   ip route add 203.0.113.10 via 192.168.3.1 dev eth0.2   # STUN и MQTT (один хост) — мимо hp0
   ```
   **Почему нужны именно эти два исключения.** `hp0` — это и есть туннель поверх 10 UDP-дыр,
   которым ещё нужно физически выбраться в интернет, чтобы держать сам туннель живым. Если
   послать default (а с ним — и трафик к VPS/STUN/MQTT) в `hp0` без исключений, получается
   замкнутый круг: пакеты, поддерживающие туннель, пытаются уйти через этот же туннель, а его
   в этот момент ещё (или уже) нет — STUN не отвечает, дыры к VPS осыпаются до 0/10, телефоны не
   пробиваются. Раньше эту роль (не пускать в `hp0` то, что не относится к LAN-клиентам) играло
   правило по источнику (`ip rule ... from 192.168.1.0/24`) — оно не трогало трафик самого
   роутера, у него была своя логика выбора маршрута. Явные хостовые маршруты проще, надёжнее
   (не зависят от `ip rule`, которое само может потеряться при `network reload`, см. ниже) и
   работают одинаково что для LAN-трафика, что для трафика самой службы `hp-router`.

   **Если WAN недоступен и в ходу резервный аплинк** (например, Wi-Fi в режиме клиента,
   `phy0-sta1`) — те же две строки, но с его шлюзом и интерфейсом вместо `eth0.2`:
   ```sh
   ip route add 203.0.113.30 via <шлюз аплинка> dev <интерфейс аплинка>
   ip route add 203.0.113.10 via <шлюз аплинка> dev <интерфейс аплинка>
   ```
   Если основной и резервный WAN переключаются автоматически (два интерфейса netifd, у каждого
   свой default в main), эти два хостовых маршрута всё равно нужно пересоздавать под тот
   аплинк, который сейчас реально работает — сами они не переезжают вместе с default.

   Ничего из этого не переживает перезагрузку или `/etc/init.d/network reload` (обычные
   `ip route`, не UCI); отдельного маршрута `203.0.113.30 via 192.168.3.1 dev eth0.2` для VPS
   раньше добивались через `uci add network.<имя>=route` — тем же способом можно закрепить и
   маршрут для STUN/MQTT, но сам `default via hp0` через UCI не заводится (`hp0` — не
   UCI-интерфейс, его поднимает сам `hp-router`), так что первую строку в любом случае придётся
   повторять руками или скриптом после каждого перезапуска `hp-router`/сети.
4. `hp0` в зону `wan` (NAT для LAN и ограничение MSS под MTU 1400):
   ```sh
   uci add_list firewall.@zone[1].device='hp0'
   uci commit firewall; /etc/init.d/firewall reload
   ```
5. Ускорение (+50% на MT7628, см. `Performance.md`): транспорт дыр мимо conntrack и программный
   flow offloading с `hp0` (штатный `flow_offloading` fw4 TUN во flowtable не включает). NAT
   остаётся. `/etc/nftables.d/90-hp-offload.nft`:
   ```
   # UDP дыр до VPS — мимо conntrack.
   chain hp_notrack_pre {
   	type filter hook prerouting priority raw; policy accept;
   	ip saddr 203.0.113.30 udp sport 40000-40999 notrack
   }
   chain hp_notrack_out {
   	type filter hook output priority raw; policy accept;
   	ip daddr 203.0.113.30 udp dport 40000-40999 notrack
   }
   # Установленные соединения LAN <-> hp0 — по быстрому пути (NAT делает flowtable).
   flowtable hpft {
   	hook ingress priority filter; devices = { eth0.1, eth0.2, hp0 };
   	counter
   }
   chain hp_offload {
   	type filter hook forward priority filter - 1; policy accept;
   	meta l4proto { tcp, udp } ct state established flow add @hpft
   }
   ```
   Входящий UDP без conntrack не попадает под «established», его надо разрешить явно:
   ```sh
   uci set firewall.hpvps=rule
   uci set firewall.hpvps.name=hp-vps-transport
   uci set firewall.hpvps.src=wan
   uci set firewall.hpvps.proto=udp
   uci set firewall.hpvps.src_ip=203.0.113.30
   uci set firewall.hpvps.src_port=40000-40999
   uci set firewall.hpvps.target=ACCEPT
   uci commit firewall; /etc/init.d/firewall reload
   ```
   `hp0` пересоздаётся при каждом запуске `hp-router` — после запуска сделать
   `/etc/init.d/firewall reload`, иначе он выпадет из flowtable. Штатный
   `firewall.@defaults[0].flow_offloading` при этом выключен.

## 3. Телефон

В приложении (`../android-vpn/README.md`): GUID телефона (`PHONE_<n>_PEER_ID`), GUID роутера
(`PHONE_<n>_MY_ID`), те же STUN и MQTT; адрес и DNS телефон получит от VPS через роутер. Телефон должен быть в
другой сети, чем роутер (например, на мобильном интернете): hairpin NAT на домашнем шлюзе
обычно не работает.

## 4. Проверка

```sh
ip route get 1.1.1.1 from 192.168.1.10 iif br-lan   # dev hp0 (LAN)
ip route get 1.1.1.1                                # через WAN (сам роутер)
ping -c3 10.80.0.1                                  # VPS внутри туннеля
```

С LAN-клиента `traceroute 1.1.1.1`: роутер → `10.80.0.1` → сеть VPS; внешний IP — VPS. В логе
роутера раз в 30 с: дыры к VPS, пакеты из TUN и в TUN, телефоны (дыры, пересылка к VPS и к
телефонам).

## 5. Откат

```sh
start-stop-daemon -K -p /tmp/hp/hp-router.pid      # hp0 исчезает вместе с процессом
# (или /etc/init.d/hp-router stop; disable — при установке во флеш)
ip route del default via 10.80.0.1 dev hp0 2>/dev/null   # если задавали (п. 3); сам hp0 маршруты уже унёс
ip route del 203.0.113.30 2>/dev/null; ip route del 203.0.113.10 2>/dev/null
rm -f /etc/nftables.d/90-hp-offload.nft; uci delete firewall.hpvps
uci del_list firewall.@zone[1].device='hp0'; uci commit firewall; /etc/init.d/firewall reload
```

## Трей и LuCI

С `CONTROL_ADDR` роутер слушает протокол управления ([`../control`](../control/README.md)):

- **LuCI → Службы → Home Proxy** — строка подключения `homeproxy-control://192.168.1.1:47001/…`:
  «Показать», «Скопировать», «Новая строка подключения» (новый ключ; прежние строки перестают
  работать сразу, телефоны это не затрагивает). Страница вызывает только `hp-router --config
  /etc/hp-router/router.env --connection-string` (право чтения) и `--new-connection-string`
  (право записи) — ACL `luci-app-homeproxy`.
- **Трей на ПК из LAN** (`hp-tray`): при первом запуске вставить строку. В окне VPS (шлюз дома) и
  телефоны с дырами и потерями, трафик LAN ↔ VPS; «Добавить телефон» — QR: роутер сам заводит
  пару GUID и свободный номер телефона, VPS выдаёт ему адрес; удалить — «Удалить телефон».
  Телефоны из `PHONE_<n>_*` удаляются только правкой `router.env`.
- Без графики, на самом роутере: `hp-router --config /etc/hp-router/router.env --connection-string`.

Проверено на Xiaomi 4C: всё перечисленное, кроме открытия страницы LuCI в браузере (права
проверены сессией rpcd). Размер `hp-router` с управлением — 2,10 МБ (без него 1,97 МБ).

## 6. Адреса, перезапуски и неполадки

**Адреса в туннеле.** Их раздаёт `vps-server`: роутер получает `10.80.0.x`, его телефоны —
`10.80.1.x` и дальше (запрос телефона роутер пересылает на VPS со своим номером телефона и
возвращает ответ). Вместе с адресом приходит DNS: резолверы VPS (или `DNS=` в `vps.env`), в
конце 8.8.8.8 и 1.1.1.1. Адрес закреплён за клиентом — за роутером по его имени, за телефоном по
«роутер + номер телефона» — и хранится в `addresses.state` рядом с `vps.env`: после перезапуска
любой стороны выдаётся тот же. Клиенты повторяют запрос раз в 30 с, так что после перезапуска
VPS маршруты к ним восстанавливаются сами. Пакет с адресом источника, выданным не этому
клиенту, VPS отбрасывает.

**Перезапуски.** Проверено 2026-09-26 (на прежнем наборе из 10 фиксированных слотов; с динамическим набором дыры
приходят по одной в 10 с, первые четыре — сразу):

| Что перезапустили | Сколько до восстановления |
|---|---|
| роутер (VPS работает) | дыры к VPS 10/10 через ~17 с; телефон — через ~90 с |
| VPS (роутер работает) | до ~80 с (окно пробива слота) |
| обе стороны сразу | несколько секунд |

Телефону после перезапуска роутера нужно до одного окна пробива (80 с): он ещё пробивается к
прежней записи роутера и переключается, когда видит новую. VPN на телефоне всё это время
остаётся включённым, адрес не меняется.

**Записи в MQTT.** Запись дыры лежит на брокере retained с TTL 60 с и переопубликуется, пока
дыра не залинкована; новая публикация на тот же топик заменяет старую. Если клиента остановили
не штатно (`force-stop`, падение), его последняя запись живёт на брокере до 60 с, и пир может
начать пробиваться к мёртвой сессии. Как только живой клиент опубликует новую запись, слот
переключается на неё сразу (раньше дожидался конца окна, а записи нескольких перезапусков
отрабатывал по очереди, по 80 с на каждую — телефон подолгу не мог подключиться). Свою дыру без ответа
пира сторона закрывает через 15 с (`RECORD_WAIT`) и пробует другую.

**Телефон в домашнем Wi-Fi.** Телефон и роутер за одним внешним адресом (телефон в той же
сети, что WAN роутера) друг до друга не пробьются: домашний шлюз не заворачивает пакет на свой
же внешний адрес (hairpin NAT). Признак — в логе роутера `пробив … на <свой внешний IP>`, живых дыр
0. Телефон должен быть на мобильном интернете или в чужой сети.

**Экран телефона выключен.** Если приложение запустить при спящем экране, Android может не дать
ему сеть: живых дыр 0, в логе пусто. Разбудить экран и перезапустить приложение.

**`firewall reload`: «Could not process rule: No such file or directory» у `flowtable hpft`.**
Любое из устройств в её списке (`devices = { eth0.1, eth0.2, hp0 }`) сейчас недоступно nft —
вся перезагрузка firewall падает с этой ошибкой, и **в системе не остаётся вообще никакого
firewall/NAT** (`nft list tables` пустой), это не «частичный» сбой. Два случая:
- `hp0` ещё не создан (роутер ждёт адрес от VPS) — дождаться `hp0` (`ip link show hp0`) и
  повторить `/etc/init.d/firewall reload`;
- `eth0.2` (или другое устройство из списка) сейчас без ссылки/адреса — например, основной WAN
  недоступен и в ходу резервный аплинк (см. п. 3). Убрать недоступное устройство из списка (или
  временно из файла целиком) и повторить reload; вернуть обратно, когда основной WAN снова жив.

**После перезагрузки роутера** маршруты, заданные руками командами `ip route add`, пропадают — как и
всё из `/tmp`. С `ROUTES=auto` (по умолчанию) маршруты (`/1` в `hp0`, `/32` до VPS, STUN и MQTT
через аплинк) ставит и снимает сама служба, она же запускается procd (`/etc/init.d/hp-router
enable`). `uci`-правила firewall и файл в `/etc/nftables.d` переживают перезагрузку сами;
перезагрузку firewall после запуска службы (flowtable с `hp0`) пока выполняют руками или хуком.

**Дыры к VPS то открываются, то теряются** (дыра открылась и через 15–30 с «потеряна»,
новые не сходятся): стороны рассинхронизировались после перезапуска одной из них. Проверить
путь до VPS без нашего кода (UDP-эхо на порт из диапазона портов дыр). Если путь есть — перезапустить
обе стороны сразу: сходятся за секунды.

## Замена `vps-client` на `hp-router` (2026-10-10, `o1`)

Роутер, где уже работает `vps-client` (маршруты, хуки DNS, раздельное туннелирование), переводится
на `hp-router` без потери настроек: тот же VPS (`VPS_SERVER`, `VPS_MY_ID`, `VPS_PEER_ID`), те же
хуки (`ON_TUN_UP`/`ON_TUN_DOWN` — абсолютные пути в `/etc/vps-client/`), тот же ключ управления
(`control.key` копируется в `/etc/hp-router/`, строка подключения трея не меняется), плюс
`STUN_ADDR`, `MQTT_ADDR`, `MQTT_CA` для телефонов. Порядок: положить бинарник во `/tmp`, собрать
`router.env`, проверить `hp-router --config … --connection-string` (бинарник запускается, настройки
читаются), потом `vps-client stop` + `disable`, `hp-router enable` + `start`, проверить дыры и
пинг, при неудаче вернуть `vps-client` (бинарник и конфиг остаются на роутере). Простой около 40 с.
Места на флеше хватило при замене без удаления старого бинарника (было 3,7 МБ свободных, стало
2,6).

## Скорость (2026-09-26)

LAN-клиент (ноутбук) → Xiaomi Mi Router 4C → VPS, iperf 2, TCP, одно соединение:

| Путь | VPS → клиент | клиент → VPS |
|---|---|---|
| напрямую через WAN роутера | 68,0 Мбит/с | 88,4 Мбит/с |
| WireGuard поверх `vps-client` (прежняя схема) | 10,2 Мбит/с | 12,1 Мбит/с |
| TUN, `vps-client` без WireGuard | 21,1 Мбит/с | 21,1 Мбит/с |
| TUN + flow offloading, `notrack`, `connect()` (п. 5) | 32,6 Мбит/с | 31,7 Мбит/с |
| **то же + подпись пакетов** (`hp-router`) | **25,4 Мбит/с** | **27,0 Мбит/с** |

Отказ от WireGuard убрал из пути пакета шифрование в ядре и лишний UDP-переход через
`127.0.0.1`: вдвое быстрее. Процессор роутера почти целиком у нашего процесса; подпись стоит
~19 мкс на пакет (по всему пакету было бы ~50). Буфер порядка на роутере под такой нагрузкой
уходит в потолок ожидания 30 мс.

Телефон на LTE (через точку доступа) → роутер → VPS → speedtest: 14 Мбит/с на приём, 7 на
отдачу.
